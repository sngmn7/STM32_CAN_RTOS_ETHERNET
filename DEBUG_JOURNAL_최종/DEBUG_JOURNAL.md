# 이더넷 간헐 장애 추적 기록 — 2026-08-01

> 하루 종일 걸린 문제 하나를 어떻게 잘못 접근했고 어떻게 찾았는지 남긴다.
> 결과보다 **과정과 실패**를 기록하는 것이 목적이다.

---

## 1. 문제

**증상**

- 전원을 인가하면 이더넷이 안 올라온다. 리셋 버튼을 누르면 그때부터 동작한다.
- 동작하더라도 수 초~수 분 뒤 멈춘다. CAN 수신 카운터까지 정지한다.
- 간헐적이다. 어떤 부팅은 5분 버티고 어떤 부팅은 2초 만에 죽는다.
- Front·Rear 두 보드 모두에서 나타난다. 증상이 보드 사이를 옮겨 다니는 것처럼 보인다.

**왜 어려웠나**

원인이 서로 다른 문제들이 **전부 "리셋하면 된다"는 같은 증상**으로 나타났다.
케이블 불량, PHY 타이밍, 캐시 ECC — 셋 다 겉보기 증상이 동일했다.

---

## 2. 최종 원인

### Cortex-M7 캐시 ECC 오류

파워온 직후 캐시 RAM 에는 임의의 노이즈가 남는다. Cortex-M7 캐시는 ECC 를 갖고
있어서 **"전체 무효화"가 아닌 범위 지정 무효화**를 수행하면, 노이즈가 든 라인에서
ECC 오류가 발생하고 BusFault(IMPRECISERR) → HardFault 로 전파된다.

`HAL_ETH_RxLinkCallback()` 이 **수신 프레임마다** `SCB_InvalidateDCache_by_Addr()`
를 호출하므로 정확히 이 경로에 걸린다.

리셋 버튼은 캐시를 정리하므로 재현되지 않는다 — 그래서 "리셋하면 된다"였다.

**수정** — `main()` 최상단, 다른 어떤 초기화보다 먼저

```c
SCB_InvalidateDCache();
```

## 3. 틀린 가설 아홉 개

| # | 가설 | 근거로 삼은 것 | 어떻게 기각됐나 |
|---|---|---|---|
| 1 | `Ethernet_Link_Periodic_Handle` 주석 처리 | 코드 읽기 | 두 빌드 다 활성인데 증상 동일 (ELF 역어셈블) |
| 2 | 불량 랜케이블 | **교차 실험 — 실제로 입증됨** | 별개 문제였다. 케이블 교체 후에도 증상 지속 |
| 3 | PHY 초기화 레이스 | 코드 경로 분석 | 디버거로 `eth_phy_retry_count = 0` 확인. PHY 는 첫 시도에 성공 |
| 4 | 스택 오버플로우 | 232 B 구조체를 스택에 올림 | `SP` 가 316 B 만 사용. 8 KB 로 늘려도 동일 |
| 5 | `DWT_LAR` 쓰기 (M7 에 없는 레지스터) | 코드 읽기 | 제거해도 동일 |
| 6 | 내가 추가한 계측/DTC 코드 전반 | "최근에 추가했으니" | 전부 비활성화해도 동일 |
| 7 | D2 SRAM 클럭 미활성 | **레지스터 실측 — 실제 결함** | 고쳐도 증상 지속. 별개 문제였다 |
| 8 | RX 버퍼 풀이 SRAM 블록 경계를 걸침 | 폴트 시 R12 값 | 12→10 으로 줄여도 동일 |
| 9 | BOR(브라운아웃 리셋) 꺼짐 | 옵션 바이트 읽기 | `BOR_LEV=0` 은 H7 **공장 기본값**. 모든 H7 이 그렇다 |

**2번과 7번은 실재하는 결함이었지만 이번 증상의 원인은 아니었다.**
"진짜 문제를 찾았다"와 "이 증상의 원인을 찾았다"는 다르다.

## 4. 무엇을 잘못했나

### 4.1 실측 전에 수정했다

아홉 번 모두 같은 패턴이었다.

```
코드에서 그럴듯한 경로 발견 → 원인이라 단정 → 수정 → 안 고쳐짐 → 다음 가설
```

수정할 때마다 변수가 하나씩 늘었다. 나중에는 "원래 문제"와 "내가 만든 문제"가
섞여서 판단이 더 어려워졌다. 실제로 5번(`DWT_LAR`)은 **내가 새로 넣은 버그**였다.

**해야 했던 것** — 가설을 세웠으면 먼저 그 가설이 맞는지 *관측*으로 확인하고,
확인된 뒤에 고친다.

### 4.2 알려진 정상 지점을 늦게 잡았다

오전에 5분간 무결점 동작한 바이너리가 있었는데, **그걸 그대로 다시 구워보는 시험을
몇 시간 뒤에야 했다.** 그 시험 하나로 "소프트웨어냐 하드웨어냐"가 갈렸다.

```
같은 바이너리(sha256 일치)가 아침엔 5분 정상, 지금은 4초 만에 사망
  -> 소프트웨어는 변수가 아니다
```

**해야 했던 것** — 간헐 장애를 만나면 가장 먼저 "마지막으로 정상이던 상태"를
재현해서 기준점을 만든다.

### 4.3 레퍼런스를 늦게 찾았다

사용자가 *"인터넷에 이런 문제 해결한 사람 있는지 레퍼런스부터 찾아봐"* 라고
지적한 뒤에야 검색했고, **ST 커뮤니티에 같은 증상·같은 콜스택·같은 해법이
이미 있었다.**

증상이 특징적일수록("파워온만 실패, 리셋은 정상") 검색이 코드 읽기보다 빠르다.

### 4.4 부정확 폴트를 정확하게 만들 생각을 늦게 했다

`IMPRECISERR` 는 **보고되는 PC 가 실제 원인과 무관**하다. 이걸 알면서도
보고된 PC(`HAL_ETH_ReadData`) 주변을 계속 뒤졌다.

## 5. 무엇이 통했나

### 5.1 디버거로 직접 읽기

추측을 끝낸 것은 전부 실측이었다.

```
CFSR = 0x400          -> IMPRECISERR (부정확 버스 오류)
eth_phy_retry_count=0 -> PHY 가설 기각
SP = 0x2404fec4       -> 스택 가설 기각 (316 B 사용)
RCC_AHB2ENR = 0       -> SRAM 클럭 결함 발견
compare-sections      -> "플래시했다"는 믿음이 틀렸음을 발견
```

특히 `compare-sections` 로 **보드에 올라간 것이 방금 빌드한 것과 다르다**는 걸
발견한 게 컸다. 그전까지 존재하지 않는 코드를 디버깅하고 있었다.

### 5.2 교차 실험

케이블을 맞바꿔서 **증상이 케이블을 따라가는지 보드를 따라가는지** 확인한 것.
5초짜리 실험으로 물리 계층을 확정했다.

```
교차 전   Front 0/8 실패     Rear 정상
교차 후   Front 6/6 정상     Rear 0/6 실패
```

### 5.3 대조군 유지

Rear 를 건드리지 않고 두어서 Front 만의 문제인지 판별할 수 있었다.
(다만 중간에 Rear 도 고치면서 대조군을 잃은 구간이 있었다 — 실수였다.)

### 5.4 마스터 스위치로 이등분

`FRONT_INSTRUMENT_ENABLE` 같은 컴파일 스위치를 만들어, 추가한 코드를
통째로 켜고 끄며 비교했다. 코드를 지웠다 되돌리는 것보다 안전하고 빠르다.

## 6. 확립한 진단 절차

### 6.1 ST-Link 직접 제어 (CubeIDE 불필요)

프로브가 여러 개여도 `sn=` 으로 지정하면 된다. **지정하지 않으면 첫 프로브에
굽는다** — 엉뚱한 보드에 플래시되는 사고의 원인이었다.

```bash
PROG=".../STM32_Programmer_CLI.exe"

$PROG -l                                                    # 프로브 목록
$PROG -c port=SWD sn=<SN> mode=HOTPLUG -r32 <주소> <개수>    # 리셋 없이 메모리 읽기
$PROG -c port=SWD sn=<SN> mode=UR reset=HWrst -w app.elf -v --start
```

**보드 식별** — 같은 MCU 가 여러 개면 리셋 벡터(`0x08000004`)를 읽어
각 ELF 의 값과 대조한다.

```bash
arm-none-eabi-objcopy -O binary app.elf app.bin
xxd -s 4 -l 4 app.bin        # 이 값과 플래시를 비교
```

### 6.2 변수 읽기

```bash
arm-none-eabi-nm --defined-only app.elf | grep <변수명>   # 주소 획득
$PROG -c port=SWD sn=<SN> mode=HOTPLUG -r32 <주소> 1      # 값 읽기
```

카운터를 시간 간격을 두고 두 번 읽으면 **증가 여부**로 살아있는지 판별할 수 있다.
이걸로 "메인 루프가 도는가", "CAN 이 수신되는가"를 디버거 없이 확인했다.

### 6.3 GDB

```bash
ST-LINK_gdbserver.exe -p 61234 -d -s -cp <프로그래머경로> -i <SN> --attach
arm-none-eabi-gdb -q -batch -x script.gdb app.elf
```

유용했던 명령:

| 명령 | 용도 |
|---|---|
| `compare-sections` | **플래시가 ELF 와 일치하는지** — 가장 먼저 확인할 것 |
| `x/4xw 0xE000ED28` | CFSR / HFSR / MMFAR / BFAR |
| `x/8xw $sp` | 예외 스택 프레임 (R0 R1 R2 R3 R12 LR PC xPSR) |
| `info symbol *(unsigned int*)($sp+24)` | 폴트 시점 PC 의 심볼 |

### 6.4 CFSR 비트 해석

| 비트 | 값 | 이름 | 의미 |
|---|---|---|---|
| 1 | 0x0002 | DACCVIOL | MPU 데이터 접근 위반 |
| 9 | 0x0200 | PRECISERR | 정확한 버스 오류 (**BFAR 유효**) |
| 10 | 0x0400 | **IMPRECISERR** | 부정확 — 버퍼된 쓰기 실패, **BFAR 무효, PC 도 무관** |
| 11 | 0x0800 | UNSTKERR | 예외 복귀 시 언스택 실패 |
| 12 | 0x1000 | STKERR | 예외 진입 시 스택 실패 |
| 24 | 0x0100_0000 | UNALIGNED | 정렬되지 않은 접근 |

> 초기에 `0x400` 을 UNSTKERR(bit11)로 잘못 읽어 스택 오버플로우 가설로 샜다.
> **비트 번호를 정확히 세라.**

### 6.5 부정확 폴트를 정확하게 — 이 프로젝트에서는 불가

MPU 를 Strongly-ordered(TEX=0) 로 바꾸면 쓰기 버퍼링이 사라져
`IMPRECISERR` → `PRECISERR` + BFAR 유효가 된다.

**시도했으나 통하지 않았다.** lwIP 가 패킷 헤더에 비정렬 쓰기를 하는데
Strongly-ordered 메모리는 비정렬 접근을 허용하지 않아, `UNALIGNED` UsageFault 가
대신 발생한다. (실측 확인)

대안: `__DSB()` 를 의심 구간 전후에 넣어 쓰기 버퍼를 강제로 비우면
폴트 지점이 그 직후로 고정된다.

## 7. 부수적으로 찾은 실재 결함

원인은 아니었지만 언젠가 터질 것들. 전부 수정했다.

### 7.1 D2 SRAM 클럭 미활성

```
RCC_AHB2ENR = 0x00000000     이더넷 버퍼가 전부 클럭 꺼진 메모리에 있었음
```

`SystemInit()` 에 활성화 코드가 있으나 `#if defined(DATA_IN_D2_SRAM)` 로
감싸여 있고 이 프로젝트는 그 매크로를 정의하지 않아 실행되지 않았다.

### 7.2 CAN `AutoBusOff = DISABLE`

`RearBody_F407` 만 `DISABLE` 이었다. 버스오프에 빠지면 소프트웨어가 재시작할
때까지 영구히 죽는다 — **이더넷과 똑같은 "리셋해야 산다" 구조.**

### 7.3 CAN 샘플점 불일치

H723 FDCAN1 은 87.5 %, F407 은 92.9 % 로 5.4 % 차이. 프레임의 약 절반이 유실됐다.

```
can500_tx=17  rx=9  bad=9        수정 전
can500_tx=20  rx=21 bad=0        수정 후 (85.7 % 로 맞춤)
```

### 7.4 RearBody_F407 이 플래시된 적 없음

소스는 500 k 로 바꿨는데 보드에는 구버전 250 k 가 올라가 있었다.
리셋 벡터 대조로 발견.

## 8. 다음에 같은 상황이면

1. **알려진 정상 지점을 먼저 재현한다.** 마지막으로 동작하던 바이너리를 그대로 굽는다.
2. **플래시가 실제로 올라갔는지 확인한다.** `compare-sections`. "성공" 표시를 믿지 않는다.
3. **증상이 특징적이면 검색부터 한다.** 코드 읽기보다 빠르다.
4. **관측으로 확인한 뒤에 고친다.** 수정은 변수를 늘린다.
5. **대조군을 유지한다.** 정상 동작하는 쪽은 건드리지 않는다.
6. **바꾼 것은 스위치로 만든다.** 되돌리기 쉬워야 이등분이 가능하다.
7. **하위 계층부터 배제한다.** 전기 → 클럭 → 메모리 → 드라이버 → 스택 → 애플리케이션.

## 10. 후속 — 지연·유실 결함 (2026-08-01 오후)

이더넷이 안정된 뒤, 같은 방법론을 성능 쪽에 적용해 결함을 더 찾았다.
정량 수치는 `METRICS.md` §5-b~§5-f 참조.

### 10.1 하행 명령 반영 지연 99.9 ms

**어떻게 찾았나** — ACK RTT 를 2000 회 재서 p99 = 0.66 ms 를 확인했다.
네트워크가 빠른데 체감 반응이 느리다면 지연은 그 뒤에 있다. 코드를 보니
`FrontCommand_SendNext()` 가 신호당 100 ms 주기로만 돌고 있었다.

**측정 설계에서 조심한 것** — 토글 간격을 100 ms 의 배수로 잡으면 항상
같은 스케줄러 위상에 걸려 지연이 상수로 나온다. 137 ms + 난수를 써서
위상을 흩뜨렸다. 결과가 평균 46.6 ms / 최대 99.9 ms 로 균등분포의
교과서적 형태로 나온 것이 측정이 올바랐다는 방증이다.

**수정** — 주기 전송은 하트비트로 두고, 값 변화 시 즉시 전송을 추가.
최소 송신 간격 10 ms 로 버스 폭주를 막았다. 99.9 ms → 175 µs.

### 10.1-b 그런데 그건 절반이었다 — 종단 지연 150 ms

하행을 99.8 % 줄이고 끝냈다고 보고했는데, **틀렸다.** 사용자가
"제일 괜찮다고 했던 게 종단 반영 RTT 아니었냐"고 되물어서 다시 봤다.

전체 경로는 하행만이 아니다.

```
Jetson 명령 ─[UDP]→ H723 ─[CAN 하행]→ F407 동작
                                          │
Jetson ←[UDP]─ H723 ←[CAN 상행 50ms]─ F407 상태
          ↑ 텔레메트리 100ms
```

내가 고친 하행은 전체의 **0.05 %** 였다. 재보니 종단 지연은 최대
150.6 ms, 평균 65.5 ms 였고 이론값 `50 + 100 = 150 ms` 와 정확히 맞았다.

**왜 놓쳤나** — 호스트에서 반영 RTT 를 재려다 포트 5102 가 점유돼 있어
장치 내부 계측으로 "대체"했는데, 그 대체품이 하행만 덮는다는 걸
확인하지 않았다. **측정 대상을 바꿀 때 무엇이 빠지는지 따지지 않은 것**이
실수다. 대체 측정은 원래 측정과 같은 것을 재야 대체가 된다.

수정은 상행 두 단계(F407 이산상태 CAN, SV 텔레메트리)에 같은 이벤트 트리거를
적용. 최대 150.6 → 27.5 ms, 평균 65.5 → 6.0 ms.

여기서 **연속량과 이산 상태를 갈랐다.** ADC 를 변화 판정에 넣으면 잡음으로
매 루프 송신이 된다. 연속량은 주기 전송, 이벤트성 신호는 변화 즉시 전송.

### 10.2 DHT11 이 CAN 인터럽트를 23 ms 차단

**어떻게 찾았나** — `can_last_error` 를 읽으니 `0x2E3` 이었고 여기에
`0x200 = HAL_CAN_ERROR_RX_FOV0`(RX FIFO 오버런)가 켜져 있었다. 비트를
하나씩 분해한 것이 시작점이다. 코드를 보니 센서 판독이 CAN 수신 IRQ 를
끈 채 `HAL_Delay(18)` 을 돌고 있었다.

**두 번째 CFSR 교훈** — 이번에도 결정타는 **에러 레지스터의 비트를
끝까지 분해한 것**이었다. 앞서 `CFSR=0x400` 을 UNSTKERR 로 잘못 읽어
헤맸던 것과 정확히 대칭이다. 이번엔 먼저 비트 정의를 확인하고 읽었다.

**측정을 먼저 했다** — 이번에는 고치기 전에 계측부터 넣었다.
`dht11_block_max_us`(DWT 실측)와 `can_fifo_overrun_count`, 그리고 H723
송신 카운터와 F407 수신 카운터를 **짝지어** 유실을 추정이 아닌 뺄셈으로
구했다. 이 순서가 §4 에서 반성한 "고치기 전에 재라"를 실제로 지킨 첫 사례다.

**수정 근거** — 데이터시트를 읽고 결정성이 실제로 필요한 구간을 갈랐다.
18 ms 스타트 펄스는 우리가 출력하고 요구가 "이상"이라 상한이 없어 인터럽트가
끼어도 무해하다. 반면 응답 40 비트는 0 이 26 µs, 1 이 70 µs 이고 문턱이
50 µs 라 끼어들면 오독한다. **임계구역을 요구사항 크기로 좁혔다.**
차단 23.1 ms → 4.1 ms, 유실률 0.696 % → 0.039 %, 센서 성공률은 91/91 유지.

### 10.3 Rear 이식 — 같은 결함 확인

Front 에서 확립한 방법을 Rear 에 그대로 적용했더니 **같은 결함이 있었다.**
하행 CAN·텔레메트리 모두 100 ms 주기 전송이었고, 지연은 최대 99.3/99.4 ms
평균 약 53 ms 로 Front 와 같은 균등분포였다. 이벤트 트리거 적용 후
하행 18 us / 텔레메트리 99 us.

**Rear 는 경로가 다르다는 걸 먼저 확인했다** — Front 는 텔레메트리가
F407 피드백(`f407_headlamp_output`)을 실어 물리 루프 폐쇄를 관측할 수 있지만,
Rear 는 RearBody 피드백이 없어 지령 자체를 싣는다. 그래서 하나의 종단 지연이
아니라 두 경로를 각각 쟀다. **Front 수치와 Rear 수치를 나란히 놓고 비교하면
안 된다**는 걸 문서에 명시했다.

**이식 중 내가 결함을 하나 만들었다** — LED 경로에서 윈도우 지령을 무조건
같이 보내게 해 윈도우가 두 경로로 나갔고 송신율이 10.7 Hz(+7 %)가 됐다.
회귀 측정을 돌리지 않았으면 "부작용 없음"이라고 잘못 보고했을 것이다.
**개선을 넣을 때마다 부작용 측정을 같이 돌린 것이 이걸 잡았다.**

### 10.5 진단 기준이 틀려 실제 고장을 놓쳤다

하위 제어기가 살아 돌아왔는데 CAN 링크가 복구되지 않는 것을 계측하다,
**진단이 그 고장을 전혀 보고하지 않는 것**을 발견했다.

판정 기준이 `BusOff` 단독이었는데, CAN 규격에 '에러 패시브 송신기가 ACK
오류를 검출했고 그동안 dominant 비트를 못 봤다면 TEC 를 올리지 않는다'는
예외가 있다. 상대 노드가 사라지면 이 예외에 걸려 **TEC 가 128 에서 멈추고
버스오프(255 초과)에 영원히 도달하지 않는다.** 실측 `TxErrorCnt = 128` 이
정확히 그 값이었다.

**"버스오프 = CAN 고장"이라는 통념이 틀렸다.** 버스오프는 *시끄러운* 버스에서
생기고, *조용한* 버스(상대 소실)에서는 에러 패시브에 머문다. 후자가 더 흔한
고장 형태인데 그걸 놓치고 있었다.

수신 두절 기반 판정을 추가해 검출 불가 → 500 ms 검출로 바꿨다. 함께 넣은
버스오프 복구(`CCCR.INIT` 해제)는 배선 재연결 시 실제로 5회 동작해 링크를
되살렸다. 이더넷의 "리셋해야 산다"(§2), RearBody 의 `AutoBusOff = DISABLE`
(§7.2)과 **같은 계열** — 셋 다 감지는 하는데 빠져나올 길이 없었다.

> **자기 시스템을 의심하는 것이 가장 어렵다.** §5-i 에서 "진단이 실제 고장을
> 잡았다"고 기록한 직후, 같은 고장의 다른 국면에서는 놓친다는 걸 발견했다.
> 한 번 통과한 시험이 그 기능을 검증했다는 뜻은 아니다.

### 10.6 RTOS 전환 — 폴트 없이 멈춘 시스템

Rear 를 CubeMX 로 FreeRTOS + lwIP `NO_SYS=0` 으로 전환했다.
정량 수치와 구성은 `METRICS.md` 6-c 절.

**가장 어려웠던 증상**

```
CFSR = 0,  HFSR = 0        크래시가 아니다
uwTick = 0 에서 정지        시간이 안 간다
CAN·텔레메트리 카운터 = 0   아무것도 안 돈다
```

폴트가 없으니 스택 추적이 무의미했다. 어제 이더넷 문제는 `CFSR=0x400` 이라는
단서라도 있었는데, 이번엔 **아무 흔적이 없었다.**

**어떻게 찾았나** — 거꾸로 물었다. "시간이 안 가려면 무엇이 필요한가?"
`uwTick` 은 타이머 인터럽트가 올리므로, **인터럽트가 꺼져 있어야** 멈춘다.
코드에서 인터럽트를 끄는 곳을 찾으니 `Error_Handler()` 였다.

```c
void Error_Handler(void) { __disable_irq(); while (1) { } }
```

그다음 "어디서 `Error_Handler()` 가 불렸나"를 좁히니 `main()` 의 UDP 서버
개설이었다. `NO_SYS=0` 전환으로 `MX_LWIP_Init()` 이 기본 태스크로 옮겨가서,
**lwIP 초기화 전에 소켓을 만들려 한 것**이다.

**교훈**

| | |
|---|---|
| 증상이 없을 때는 거꾸로 묻는다 | "이 증상이 나오려면 무엇이 참이어야 하나" |
| RTOS 전환은 코드 이동이 아니다 | **초기화 순서와 실행 문맥의 재배치**다 |
| 컴파일러는 순서를 안 잡아준다 | `MX_LWIP_Process()` 는 링크 에러로 잡혔지만 초기화 순서는 못 잡음 |
| 임의 마커는 보호받지 못한다 | `USER CODE BEGIN PHY_SETTLE` 이 통째로 사라졌다 |

> 어제 넣은 버스오프 자동 복구(§10.5)가 이날 다시 값을 했다. 검증 중
> 배선 접촉 불량으로 두 CAN 버스가 동시에 버스오프에 빠졌는데, 복구
> 로직이 **114회 재시도**하다 배선이 회복되자 자동으로 살려냈다.
> 그 로직이 없었으면 수동 리셋이 필요했다.

### 10.7 이번에 배운 것

| 교훈 | 근거 |
|---|---|
| 에러 레지스터는 비트 단위로 분해한다 | `0x2E3` 안에 RX_FOV0 가 숨어 있었다 |
| 고치기 전에 계측을 먼저 넣는다 | 전/후 비교가 추정이 아닌 뺄셈이 됐다 |
| 유실은 짝지어 센다 | 한쪽 카운터만으로는 유실을 알 수 없다 |
| 측정 도구부터 의심한다 | 주입기의 100 ms 송신 주기가 81 ms 편향을 만들었다 |
| 위상이 있는 주기 시스템은 위상을 흩뜨려 잰다 | 100 ms 배수로 재면 지연이 상수로 보인다 |
| 임계구역은 요구사항 크기로 좁힌다 | 18 ms 중 실제 필요한 건 4 ms 뿐이었다 |
| 개선의 부작용을 같은 창에서 확인한다 | 지연 −99.8 % 에 버스 부하 +1.9 % 임을 함께 쟀다 |
| **대체 측정은 무엇이 빠지는지 먼저 따진다** | 하행만 재놓고 종단을 잰 줄 알았다 (§10.1-b) |
| 계측값끼리 모순되는지 교차 확인한다 | `1ms 초과 = 전체 표본`인데 `최소 = 0` → 초기화 누락 |
| 개선 폭이 크면 대상이 맞는지 되짚는다 | −99.8 % 인데 체감이 그대로면 다른 데 지배항이 있다 |
| **증상이 없을 때는 거꾸로 묻는다** | "이 증상이 나오려면 무엇이 참이어야 하나" (§10.6) |
| **RTOS 전환은 초기화 순서의 재배치다** | 컴파일러가 안 잡아주는 유일한 부분 (§10.6) |
| CubeMX 는 자기가 만든 마커만 지킨다 | 임의 `USER CODE` 마커는 통째로 사라진다 |

> **측정 도구 자체의 함정 하나** — `STM32_Programmer_CLI -r32 <addr> <N>`
> 의 `N` 은 워드가 아니라 **바이트**다. `perf_stat_t`(6×u32)를 읽으려고
> `6` 을 줬더니 8 바이트만 읽혀 max/avg 가 빈칸으로 나왔다.
> 출력의 `Size : 8 Bytes` 를 보고 알아챘다. **도구 출력을 끝까지 읽자.**

### 10.8 Front RTOS 전환 — 세 번의 assert, 하나의 원인

Rear 와 같은 절차로 Front 를 `NO_SYS=0` 전환했는데 보드가 응답하지 않았다.
정량 데이터는 `METRICS.md` §6-e. 여기에는 **추적 순서**만 남긴다.

#### 관측

| 항목 | 값 | 해석 |
|---|---|---|
| CFSR / HFSR | 0 / 0 | HardFault 아님 |
| `xTickCount` | 1721 → 1721 (5 초) | **커널이 정지** |
| `uwTick` | 1722 | 틱과 같은 순간 멈춤 |
| `pxCurrentTCB` | `tcpip_thread` | 그때 돌던 태스크 |
| `can250_rx_count` | 615 | 잠시는 정상 동작 |

폴트가 아니면서 인터럽트가 꺼진 채 멈췄다 →
`taskDISABLE_INTERRUPTS(); for(;;);` 뿐이다 → `configASSERT` 또는 `Error_Handler`.

#### 추적

```
1) configASSERT 에 __FILE__/__LINE__ 기록 추가
   -> lwip/core/mem.c:639  "double free"

2) 앱 콜백 전수 확인 -> 이중 해제 없음
   -> 경쟁이다. NO_SYS=0 이면 tcpip_thread 와 net 태스크가 동시에 lwIP 를 만진다
   -> LOCK_TCPIP_CORE() 적용 (진짜 결함 하나 해소)

3) 증상이 옮겨감:  queue.c:1278  configASSERT(pxQueue->uxItemSize == 0)
   생존 1721 -> 6083 틱
   그런데 이건 "ISR 이 주는 세마포어가 세마포어가 아니다" 라는 뜻
   -> 코드상 불가능. 메모리 오염이다.

4) assert 추적을 멈추고 감시 장치를 켠다
   vApplicationStackOverflowHook 이 비어 있었다  <- 여기가 갈림길
   -> overflow task = "EthIf"

5) 근본 원인: CMSIS-RTOS v2 stack_size 는 워드가 아니라 바이트
   INTERFACE_THREAD_STACK_SIZE (350) = 350 B = 87 워드
   실측 사용량 404 B  -> 54 B 초과
```

#### 왜 오래 걸렸나

1 번과 3 번을 **각각 독립된 버그로 봤다.** 실제로는 4 번이 유일한 원인이고
앞의 둘은 넘친 스택이 `heap_4` 인접 블록을 덮어쓴 결과였다.

전환점은 3 번 assert 의 **내용이 코드상 성립할 수 없다**는 것을 알아챈
순간이었다. 그 이후로는 "어디서 죽었나" 가 아니라 "무엇이 메모리를
망가뜨렸나" 로 질문을 바꿨고, 그러자 감시 장치를 켜는 게 자연스러운 다음
수순이 됐다.

#### 켜져 있는 검사 ≠ 동작하는 검사

`configCHECK_FOR_STACK_OVERFLOW = 2` 는 **처음부터 켜져 있었다.**
CubeMX 가 만든 훅 본문이 비어 있었을 뿐이다. 감지는 부팅 1.7 초 만에
정확히 되고 있었는데 아무도 듣지 않았다.

같은 이유로 `vApplicationMallocFailedHook` 도 비어 있었다. 지금은 셋 다
(assert / 스택 오버플로 / malloc 실패) 기록하고 멈춘다.

#### 곁가지에서 건진 것

- `tcpip_thread` 여유가 196 B(19 %) 뿐이었다. 안 터졌을 뿐 다음 차례였다.
  같은 측정으로 미리 찾아 2048 B 로 올렸다.
- lwIP 코어 락 누락은 **Rear 에도 그대로 있었다.** 증상이 없었지만
  같은 구조이므로 선제 적용했다.
- PC 의 유선 어댑터가 `192.168.56.1/24`(VirtualBox 호스트 전용)로 바뀌어
  존 네트워크 경로가 사라져 있었다. **한동안 정상 보드를 고장으로 오판했다.**
  Rear 를 대조군으로 같이 ping 해서 알아챘다 —
  둘 다 실패하면 보드가 아니라 경로를 의심한다.

#### 이번 항목의 교훈

| 교훈 | 근거 |
|---|---|
| **assert 위치는 발각 지점이지 발생 지점이 아니다** | mem.c → queue.c 는 둘 다 오염의 결과 |
| **"코드상 불가능한" assert 는 메모리 오염 신호다** | ISR 세마포어가 세마포어가 아니라고 나옴 |
| **켜져 있는 검사와 동작하는 검사는 다르다** | 오버플로 검사 2, 훅 본문 비어 있음 |
| 단위를 의심한다 (워드 vs 바이트) | CMSIS `stack_size` = 바이트, `-r32 N` = 바이트 |
| 하나 찾으면 같은 구조를 전부 훑는다 | 스택 여유를 6 개 스레드 전부 재서 tcpip 도 찾음 |
| 같은 코드 구조면 다른 보드도 본다 | 코어 락 누락을 Rear 에 선제 적용 |
| **대조군 없이 실패를 판정하지 않는다** | PC 경로 소실을 보드 고장으로 오판 |

### 10.9 공유기를 바꿨더니 보드가 사라졌다 (2026-08-06)

존 네트워크(유선)가 공유기 DHCP 대역에 얹혀 있었다. NEXTU 로 교체하자
젯슨 유선이 `172.30.1.73` → `192.168.1.60` 으로 따라갔는데, 보드는 정적
`172.30.1.200/201` 이라 서브넷이 갈렸다.

```
enP8p1s0  UP <LOWER_UP>      <- 물리 링크는 처음부터 정상
          192.168.1.60/24    <- 새 DHCP 대역
보드      172.30.1.200/.201  <- 펌웨어 고정
-> ping 0/5
```

**증상은 '이더넷 고장' 처럼 보이지만 링크는 멀쩡했다.** `ip -br link` 의
`LOWER_UP` 을 먼저 봤기 때문에 물리층을 빨리 배제할 수 있었다.

조치는 보드를 새 대역으로 옮기는 것이었고, **주소가 박혀 있는 곳이 5 군데**
였다 (COMM_ICD §0 에 표로 정리). 그중 `lwip.c` 의 IP 블록은 USER CODE 구역
밖이라 CubeMX 가 덮어쓴다 — 재생성 때마다 확인해야 한다.

조치 후 ping 30/30 무손실, HMI 폐루프 8/8 통과로 검증했다.

| 교훈 | 근거 |
|---|---|
| **링크와 주소를 먼저 분리해서 본다** | `LOWER_UP` 이면 물리층은 정상, IP 문제다 |
| 정적 주소는 인프라 변경에 취약하다 | DHCP 대역에 정적 노드를 얹으면 공유기가 바뀔 때 끊긴다 |
| **박힌 주소는 한곳에 목록화한다** | 5 군데를 찾아다니지 않으려면 문서가 있어야 한다 |
| 남의 DHCP 주소를 고정으로 알면 안 된다 | 젯슨이 재할당되면 텔레메트리가 또 끊긴다 → 공유기에 예약 |
