## 1. 이더넷 파워온 실패 — 근본 원인 해결

### 측정 조건
- Front H723 (STM32H723ZG), lwIP 2.2.1 NO_SYS=1
- Jetson 에서 `ping -I enP8p1s0 172.30.1.201`

### 개선 전

| 관측 | 값 |
|---|---|
| 파워온 후 동작 | **불가** — 리셋 버튼을 눌러야 시작 |
| 리셋 후 생존 시간 | 2 초 ~ 5 분 (부팅마다 다름) |
| 정지 시 상태 | HardFault, CAN ISR 포함 전 기능 정지 |
| `CFSR` | `0x00000400` (IMPRECISERR) |
| 폴트 위치 | `HAL_ETH_ReadData` → `HAL_ETH_RxLinkCallback` |
| 동일 바이너리 재현성 | sha256 일치 바이너리로 100 % 재현 |

**결정적 관측** — 오전에 171/171(100 %) 무결점 동작한 바이너리를 그대로 재플래시했을 때도 4 초 만에 동일 HardFault. → 소프트웨어는 변수가 아님을 확정.

### 개선 후

```
전원 재인가 (리셋 없음)      정상 부팅
60 초 연속 관찰              FRONT 20/20 UP,  REAR 20/20 UP
ping 30 회                   30/30, 손실 0 %, 평균 0.27 ms (min 0.234 / max 0.305)
CFSR                         0x00000000 (폴트 흔적 없음)
연속 가동                    1595 초 시점 정상 동작 확인
```

### 원인과 수정

파워온 직후 Cortex-M7 캐시 RAM 의 노이즈 데이터 + 캐시 ECC 조합.
범위 지정 무효화(`SCB_InvalidateDCache_by_Addr`)가 ECC 오류를 유발하고
BusFault 로 전파. 리셋은 캐시를 정리하므로 재현되지 않음.

```c
/* main() 최상단 */
SCB_InvalidateDCache();
```

> **자소서 문장 예시**
> "전원 인가 시에만 이더넷이 동작하지 않고 리셋 시에는 정상인 간헐 장애를 추적.
> ST-Link GDB 로 `CFSR=0x400`(부정확 버스 오류)를 확인하고, 동일 바이너리
> (sha256 일치)가 재현됨을 근거로 소프트웨어 원인을 배제. Cortex-M7 캐시 ECC 와
> 이더넷 드라이버의 범위 지정 캐시 무효화가 충돌하는 문제로 특정하고,
> 부팅 시 전체 무효화를 추가해 파워온 성공률을 0 %→100 % 로 개선."

| F407 CAN1 | 14 (BS1 12 / BS2 1) | **92.9 %** |

**차이 5.4 %** — 정상 동작하는 250 kbps 버스는 1.8 % 차이.

## 4. DTC 오검출 — tick 언더플로우

### 개선 전

정상 수신 중에도 센서 DTC(`P0500`/`P0501`/`P0502`)가 `PENDING` ↔ 해제를 초당 수 회 반복.

**원인** — `now` 는 메인 루프 시작에 캡처되고 `last_tick` 은 CAN ISR 이 갱신한다.
ISR 이 `now` 이후에 들어오면 `last_tick > now` 가 되어 부호 없는 뺄셈이
언더플로우(약 43억) → 타임아웃 오검출.

```c
/* 문제 코드 */
(uint32_t)(now - last_tick) > REAR_SENSOR_LOST_MS
```

### 개선 후

```c
static uint8_t Rear_SensorLost(uint32_t last_tick, uint32_t now)
{
    if ((int32_t)(now - last_tick) < 0) return 0U;   /* 미래 = 방금 수신 */
    return ((uint32_t)(now - last_tick) > REAR_SENSOR_LOST_MS) ? 1U : 0U;
}
```

```
25 초 / 51 패킷 관찰 — 센서 DTC 상태 전이 0 회
```

> **자소서 문장 예시**
> "ISR 과 메인 루프가 시각을 공유하는 구조에서 부호 없는 뺄셈 언더플로우로
> 진단 오검출이 발생하는 문제를 발견하고, 부호 있는 비교로 교정해 오검출을 제거."

## 5. DTC 검출 시간 — 설계값 대비 실측

장치가 스스로 측정해 보고하는 `detect_ms` 필드로 검증.

| DTC | 설정 `confirm_ms` | 실측 `detect_ms` | 오차 |
|---|---|---|---|
| U0100 (존간 링크 상실) | 1000 | **1000** | 0 |
| U0300 (호스트 링크 상실) | 1500 | **1500** | 0 |

슈퍼루프가 38,660 Hz 로 돌아 디바운스 만료를 26 µs 내에 포착하기 때문.

**검출 시간 분해**

```
U0300 총 검출시간 = 링크 타임아웃 500 ms + 디바운스 확정 1500 ms = 2000 ms
```

### 고장 주입 12 사이클 실측

Jetson 이 명령 송신을 끊고, `'SD'` 채널에서 `U0300` 이 `TEST_FAILED` 로
전이하는 시각을 같은 시계로 측정. 명령 재개 후 해제까지도 함께 잰다.
(`fault_inject.py -n 12` → `inject12.csv`)

| 항목 | 설계값 | 평균 | 최소 | 최대 | **σ** |
|---|---|---|---|---|---|
| 검출 (호스트 실측) | 2000 ms | 1919.2 | 1917.9 | 1922.0 | **1.5 ms** |
| 검출 (장치 자체 보고) | 1500 ms | **1500.0** | 1500 | 1500 | **0.0** |
| 치유 (해제) | 3000 ms | 3004.2 | 2995.7 | 3088.0 | 25.3 ms |

**σ = 1.5 ms.** 12 사이클 전 구간에서 검출 시간이 사실상 상수다.

> **호스트 실측이 설계값보다 81 ms 짧은 이유** — 주입기가 `t0` 를 "송신
> 중단 시각"으로 기록하는데 `CMD_PERIOD = 100 ms` 라 실제 마지막 패킷은
> 최대 100 ms 먼저 나간다. 장치 타임아웃 창은 그때부터 시작하므로 호스트가
> 재는 값이 그만큼 짧아진다. **장치 오차가 아니라 측정 기준점 편향**이고,
> 장치가 스스로 보고한 `detect_ms` 는 12 회 모두 정확히 1500 ms 였다.
> 이 편향을 발견한 것 자체가 "측정 도구를 먼저 검증한다"의 사례다.

## 5-b. 명령 왕복 지연(ACK RTT) — Jetson ↔ Front

명령 패킷을 보내고 Front 가 그대로 반향한 패킷이 돌아오기까지.
순수 네트워크 + 파싱 경로만 본다. (`rtt_probe.py -a 2000`)

| n | 최소 | p50 | p95 | p99 | 최대 | σ | 손실 |
|---|---|---|---|---|---|---|---|
| 2000 | 0.186 ms | **0.239 ms** | 0.560 ms | **0.663 ms** | 0.835 ms | 0.090 ms | **0/2000** |

명령 경로 전체가 서브밀리초이고 꼬리도 1 ms 를 넘지 않는다.
**따라서 아래 §5-c 의 지연은 네트워크가 아니라 CAN 송신 스케줄러에서 온다.**

> **호스트에서 재는 반영 RTT 는 포기했다** — 텔레메트리 포트 5102/5002 를
> Jetson 애플리케이션이 점유 중이라 관측 소켓을 붙일 수 없었다. 대신 장치
> 안에서 루프 전체를 직접 재는 방식으로 전환했다(§5-e). 빠지는 것은 양끝의
> UDP 편도 구간(각 약 0.12 ms)뿐이고, 이는 위 표에서 이미 측정돼 있으며
> 종단 지연 수십 ms 대비 0.3 % 미만이라 결론을 바꾸지 않는다.

## 5-c. 하행 명령 반영 지연 — 주기 전송 → 이벤트 트리거

> **이것은 종단 지연의 하행 절반이다.** 상행까지 포함한 전체 제어 루프는
> §5-d 를 봐야 한다. 여기만 고쳤을 때 종단 지연은 거의 줄지 않았다.

### 문제

`FrontCommand_SendNext()` 는 7 개 하행 신호를 라운드로빈으로 돌리며
**신호당 100 ms 주기**로만 내보냈다. Jetson 명령이 0.24 ms 만에 도착해도
그 값이 CAN 으로 나가려면 자기 슬롯을 기다려야 한다.

```
Jetson 명령 --0.24ms--> H723 수신/적용 --[0~100ms 대기]--> CAN 송신 --> F407 동작
                                          ^^^^^^^^^^^^^^
                                          전체 지연의 99.8 %
```

### 측정 방법

값이 바뀐 시각(`DWT->CYCCNT`)부터 그 신호가 실제로 TX FIFO 에 들어간
시각까지를 장치 안에서 직접 잰다. 분해능 5.2 ns.
스케줄러 위상에 고르게 분포시키려고 토글 간격을 100 ms 의 배수가 아닌
137 ms + 난수(0~50 ms)로 잡았다. (`cmd_toggle.py -n 300`)

### 결과 — 동일 조건 302 표본

| | 개선 전 (주기 전송) | 개선 후 (이벤트 트리거) | 개선폭 |
|---|---|---|---|
| 최대 | **99,900 µs** (99.9 ms) | **175 µs** | **−99.8 %** |
| 평균 | 46,556 µs (46.6 ms) | **34 µs** | −99.9 % |
| 1 ms 초과 | **294 / 302** | **0 / 302** | 전면 해소 |

> 이 측정 당시 `min_us` 는 초기화 누락으로 0 에 고정돼 있어 표에서 뺐다.
> 원인과 수정은 §5-d 끝에 적었다. 최대·평균·표본수는 영향받지 않는다.

개선 전 수치가 **평균 46.6 ms ≈ 50, 최대 99.9 ms ≈ 100** 으로 나온 것은
0~100 ms 균등분포의 교과서적 형태다. 이론과 실측이 맞아떨어져 원인 특정이
정확했음을 뒷받침한다.

### 수정

```c
/* 변화 시 즉시 전송하되 같은 신호의 최소 송신 간격은 지킨다. */
#define FRONT_COMMAND_MIN_GAP_MS   10U

static uint8_t FrontCommand_Due(uint8_t idx, uint32_t now, uint32_t last_tx_tick)
{
    uint32_t age = (uint32_t)(now - last_tx_tick);

    if ((idx < FC_SIG_COUNT) && (fc_pending[idx] != 0U))
    {
        return (age >= FRONT_COMMAND_MIN_GAP_MS) ? 1U : 0U;
    }
    return (age >= FRONT_COMMAND_TX_PERIOD_MS) ? 1U : 0U;
}
```

주기 전송(하트비트)은 그대로 두고 변화분만 앞당긴다. 최소 간격 10 ms 는
AUTOSAR COM 의 minimum delay time 과 같은 취지로, 값이 빠르게 흔들려도
버스를 채우지 않게 막는 안전장치다.

### 회귀 확인 — 부작용 없음

| | 개선 전 | 개선 후 |
|---|---|---|
| 하행 송신율 | 70.1 Hz | **71.4 Hz** (+1.9 %) |
| 하행 유실률 | 0.039 % | **0.035 %** |
| TX 에러 / busy | 0 / 0 | **0 / 0** |

지연을 99.8 % 줄이면서 버스 부하는 2 % 미만 증가에 그쳤다.

> **자소서 문장 예시**
> "제어 명령의 반영 지연을 장치 내부 사이클 카운터로 계측해 최대 99.9 ms 임을
> 확인하고, 그 99.8 % 가 네트워크가 아니라 CAN 송신 스케줄러의 100 ms 주기
> 대기임을 ACK RTT(p99 0.66 ms) 와 대조해 분리. 주기 전송에 이벤트 트리거를
> 결합하고 최소 송신 간격으로 버스 폭주를 막아, 최대 지연을 99.9 ms → 175 µs
> 로 줄이면서 버스 부하 증가는 2 % 미만으로 억제."

## 5-d. 종단 반영 지연 — 제어 루프가 실제로 닫히는 시간 ★

**이 항목이 사용자가 체감하는 지연이고, 위 §5-c 는 그 일부일 뿐이다.**

### 전체 경로

```
Jetson 명령 ─[UDP 0.12ms]→ H723 ─[CAN 하행]→ F407 동작
                                                  │
Jetson ←[UDP 0.12ms]─ H723 ←[CAN 상행 50ms]─ F407 상태
              ↑ SV 텔레메트리 100ms
```

§5-c 에서 **하행만** 고쳤다. 상행 두 단계(F407 상태 CAN 50 ms, SV 텔레메트리
100 ms)는 손대지 않았으므로, 고친 뒤에도 종단 지연은 그대로 남아 있었다.

### 측정 방법

`front_headlamp_command` 가 바뀐 시각부터, **F407 이 CAN 으로 되돌려준**
`f407_headlamp_output` 이 실린 SV 패킷이 실제로 송신되는 시각까지를
장치 안에서 잰다. 피드백 값을 쓰므로 루프가 물리적으로 닫힌 것을 확인한다.

```c
/* 패킷이 실제로 나갔고(ft_tx_count 증가), 그 패킷이 F407 피드백을 담을 때만 */
if ((refl_pending != 0U) && (ft_tx_count != tx_before) && (v.headlamp == refl_target))
{
    Perf_Update(&perf_reflect_latency, PERF_ELAPSED(refl_cycle));
    refl_pending = 0U;
}
```

표본 엄밀성을 위해 **피드백이 이미 목표값이면 표본에서 제외**한다.
직전 지령이 아직 반영 중이면 루프가 닫히는 순간을 관측할 수 없어
0 µs 로 잘못 집계되기 때문이다.

### 결과 — 동일 조건 300 표본

| | 개선 전 (상행 주기 전송) | 개선 후 (상행 이벤트 트리거) | 개선폭 |
|---|---|---|---|
| **최대** | **150,569 µs** (150.6 ms) | **27,489 µs** (27.5 ms) | **−81.7 %** |
| **평균** | 65,514 µs (65.5 ms) | **5,985 µs** (6.0 ms) | **−90.9 %** |
| 최소 | (계측 결함, 아래 참조) | 652 µs | — |
| 표본 | 299 | 300 | — |

개선 전 최대 150.6 ms 는 이론값 **50 ms(상행 CAN) + 100 ms(텔레메트리)
= 150 ms** 와 정확히 일치한다. 두 주기의 합이 지연의 정체였다.

### 수정 — 상행 두 단계 모두 이벤트 트리거

**① F407 → H723 (CAN 이산 상태 7 종)**

```c
static uint8_t CAN1_StatusDue(uint32_t now, uint32_t last_tx_tick,
                              uint8_t current, uint8_t prev)
{
  uint32_t age = (uint32_t)(now - last_tx_tick);

  if (current != prev)
  {
    return (age >= CAN_STATUS_MIN_GAP_MS) ? 1U : 0U;   /* 10 ms */
  }
  return (age >= CAN_PERIOD_DIGITAL_STATUS_MS) ? 1U : 0U;   /* 50 ms */
}
```

**② H723 → Jetson (SV 텔레메트리)**

```c
/* 이산 상태만 변화 판정에 넣는다. ADC 는 잡음으로 매 루프 흔들려서
   넣으면 사실상 매 바퀴 송신이 된다. */
changed = (turn_left != prev) || (turn_right != prev) ||
          (headlamp != prev) || (busoff != prev) || (dht_valid != prev);
```

**연속량(ADC)과 이산 상태를 구분한 것이 핵심 판단이다.** 조향/브레이크/가속
ADC 를 변화 판정에 넣으면 잡음 때문에 매 루프 송신이 되어 버린다. 연속량은
주기 전송으로, 이벤트성 신호는 변화 즉시 전송으로 나눴다.

### 잔여 27.5 ms 의 정체

세 개의 10 ms 양자화가 직렬로 남아 있다.

```
F407 제어 루프 주기 10 ms + CAN 최소간격 10 ms + 텔레메트리 최소간격 10 ms
```

최소 간격을 더 줄이면 더 내려가지만 버스·CPU 부하와 맞바꾸는 것이라
여기서 멈췄다. 평균 6 ms 는 이 시스템 용도에 충분하다.

### 회귀 확인 — 무부하 송신율 불변

| 신호 | 설계 | 실측 |
|---|---|---|
| SV 텔레메트리 | 10 Hz | **10.2 Hz** |
| 헤드램프 상태 CAN | 20 Hz | **20.4 Hz** |
| 방향지시 좌 CAN | 20 Hz | **20.4 Hz** |
| 토글스위치 CAN | 20 Hz | **20.4 Hz** |
| 조향 ADC CAN (대조군) | 50 Hz | **50.5 Hz** |

값이 안 바뀌면 주기 전송 그대로다. **부하 증가는 상태가 실제로 바뀔 때만**
발생하고, 최소 간격이 상한을 보장한다.

> **자소서 문장 예시**
> "제어 명령이 반영돼 상태로 되돌아오기까지의 종단 지연을 장치 내부 사이클
> 카운터로 계측해 최대 150.6 ms 를 확인. 이론값(상행 CAN 50 ms + 텔레메트리
> 100 ms)과 일치함을 근거로 원인을 주기 전송 구조로 특정했다. 연속량과
> 이산 상태를 분리해 이산 신호에만 이벤트 트리거를 적용하고 최소 송신 간격으로
> 상한을 걸어, 종단 지연을 최대 150.6→27.5 ms, 평균 65.5→6.0 ms 로 줄이면서
> 정상 상태 버스 부하는 불변으로 유지."

> **계측 결함 하나를 스스로 잡았다** — `perf_stat_t` 를 BSS 기본값 0 으로
> 두는 바람에 `min_us` 가 0 에 고정돼 있었다. `1ms 초과 = 전체 표본 수`
> 인데 `최소 = 0` 인 모순을 보고 알아챘다. `{0, UINT32_MAX, 0, 0, 0, 0}`
> 으로 초기화해 고쳤다. **계측값끼리 모순되는지 교차 확인하자.**

## 5-e. Rear 지연 — Front 방법론 이식

Front 에서 확립한 방법을 Rear 에 그대로 적용했다. **같은 결함이 있었다.**

```
Rear H723   LED_CMD_TX_PERIOD_MS      100U   ← 하행, 주기 전송
            WINDOW_CMD_TX_PERIOD_MS   100U   ←
            RT_PERIOD_MS              100U   ← 텔레메트리, 주기 전송
```

### Rear 는 경로가 다르다

Front 는 텔레메트리가 `f407_headlamp_output`(F407 피드백)을 실어 물리 루프가
닫히는 것을 관측할 수 있었다. **Rear 는 RearBody 로부터 출력 상태 피드백이
없어** 텔레메트리가 지령 자체(`led_brake_command`)를 싣는다.
따라서 하나의 종단 지연이 아니라 **두 경로를 각각** 잰다.

| 경로 | 의미 |
|---|---|
| `perf_rear_cmd_latency` | 지령 변화 → 하행 CAN 송신 (실제 구동 경로) |
| `perf_rear_reflect_latency` | 지령 변화 → SR 텔레메트리 송신 (Jetson 이 보는 시점) |

### 결과 — 각 300 표본, 브레이크등 토글

| 경로 | | 개선 전 | 개선 후 | 개선폭 |
|---|---|---|---|---|
| 하행 CAN | 최대 | **99,308 µs** (99.3 ms) | **18 µs** | **−99.98 %** |
| | 평균 | 52,942 µs (52.9 ms) | **17 µs** | −99.97 % |
| | 1 ms 초과 | 296 / 300 | **0 / 300** | 전면 해소 |
| 텔레메트리 | 최대 | **99,403 µs** (99.4 ms) | **99 µs** | **−99.9 %** |
| | 평균 | 52,996 µs (53.0 ms) | **82 µs** | −99.8 % |
| | 1 ms 초과 | 296 / 300 | **0 / 300** | 전면 해소 |

개선 전 두 경로 모두 최대 ≈ 99.4 ms, 평균 ≈ 53 ms 로 **0~100 ms 균등분포**다.
Front 와 완전히 같은 형태이고, 원인도 같다.

개선 후 산포가 거의 없다(하행 17~18 µs). 토글 간격 약 180 ms 가 최소 간격
10 ms 를 항상 넘어서, 변화가 다음 루프 바퀴에 그대로 나가기 때문이다.

### Front 대비 왜 더 좋은가

Rear 텔레메트리(99 µs)가 Front 종단 지연(27.5 ms)보다 훨씬 작은 것은
**측정 대상이 다르기 때문이지 Rear 가 우월해서가 아니다.**
Front 는 CAN 왕복과 F407 제어주기를 포함한 물리 루프를 재고,
Rear 는 피드백이 없어 지령이 텔레메트리에 실리는 시점까지만 잰다.
**Rear 에 출력 피드백을 추가하면 같은 기준으로 비교할 수 있다** — 미해결 항목.

### 회귀 확인 — 무부하 송신율 불변

| 신호 | 설계 | 실측 |
|---|---|---|
| LED 지령 CAN | 10 Hz | **10.2 Hz** (30.5 Hz / 3 프레임) |
| 윈도우 지령 CAN | 10 Hz | **10.2 Hz** |
| SR 텔레메트리 | 10 Hz | **10.2 Hz** |

> **중간에 만든 결함 하나** — 처음에는 LED 경로에서 윈도우 지령을 무조건
> 같이 보내게 해서 윈도우가 두 경로로 나가 **10.7 Hz(+7 %)** 가 됐다.
> 송신율을 재보고 알아챘다. 값이 실제로 바뀐 경우에만 앞당겨 보내도록
> 고쳐 10.2 Hz 로 복귀. **"부작용 없음"은 주장이 아니라 측정이어야 한다.**

### 비교 측정을 위한 스위치

값마다 재빌드가 필요하므로 개선 전/후를 같은 코드에서 전환할 수 있게 남겼다.

```c
/* 0 = 순수 주기 전송(개선 전, 비교 측정용) / 1 = 이벤트 트리거 */
#define REAR_EVENT_TRIGGER_ENABLE   1
```

## 5-f. DHT11 인터럽트 차단 — CAN 프레임 유실

### 문제

`DHT11_ReadSensor()` 가 센서 판독 전 구간에서 CAN 수신 인터럽트를 껐다.

```c
HAL_NVIC_DisableIRQ(CAN1_RX0_IRQn);
HAL_Delay(DHT11_START_LOW_MS);     /* 18 ms - 우리가 출력하는 스타트 펄스 */
... 40비트 판독 ~4 ms ...          /* 여기만 실제로 타이밍이 중요 */
```

STM32F4 의 CAN RX FIFO 는 **3 단**이다. 하행 명령이 70 Hz 로 오는데
23 ms 를 막으면 4 번째 프레임부터 오버런으로 사라진다.

### 측정

`DWT` 로 차단 구간을 직접 재고, `HAL_CAN_ERROR_RX_FOV0` 를 세는 카운터를
추가했다. 유실은 H723 의 송신 카운터와 F407 의 수신 카운터를 짝지어
직접 뺀 값이다(추정 아님). 창 180 초.

| | 개선 전 | 개선 후 | 개선폭 |
|---|---|---|---|
| **IRQ 차단 최대** | **23,085 µs** | **4,098 µs** | **−82.3 %** |
| 하행 송신 (H723) | 12,782 | 12,782 | — |
| 하행 수신 (F407) | 12,693 | **12,777** | — |
| **유실** | **89** | **5** | −94.4 % |
| **유실률** | **0.696 %** | **0.039 %** | −94.4 % |
| RX FIFO 오버런 | 21 | **3** | −85.7 % |
| **DHT11 판독 성공** | **91 / 91** | **91 / 91** | **무회귀** |

### 수정

18 ms 스타트 펄스는 **우리가 출력하는 신호**이고 데이터시트 요구가
"18 ms 이상"이라 상한이 없다. 이 구간에 인터럽트가 끼어들어도 펄스가
조금 길어질 뿐 무해하다. 반면 센서 응답 40 비트는 0 이 26 µs, 1 이 70 µs 로
판정 문턱이 50 µs 라서 인터럽트가 비트 중간에 끼면 오독한다.
**요구사항이 실제로 결정성을 필요로 하는 구간만 남겼다.**

```c
/* 스타트 펄스는 인터럽트 허용 */
DHT11_SetPinOutput();
HAL_GPIO_WritePin(..., GPIO_PIN_RESET);
HAL_Delay(DHT11_START_LOW_MS);

/* 여기서부터만 차단 */
HAL_NVIC_DisableIRQ(CAN1_RX0_IRQn);
...
```

**DHT11 판독 성공률이 91/91 로 그대로**인 것이 핵심이다. 타이밍을 희생해
얻은 개선이 아니라, 불필요하게 넓던 임계구역을 정확히 좁힌 것이다.

> **자소서 문장 예시**
> "온습도 센서 판독이 CAN 수신 인터럽트를 23 ms 간 차단해 3 단 RX FIFO 가
> 넘치고 하행 명령의 0.70 % 가 유실되는 것을 계측으로 확인. 데이터시트를
> 근거로 결정성이 실제로 필요한 구간(응답 40 비트, 비트 판정 문턱 50 µs)과
> 불필요한 구간(하한만 있는 18 ms 스타트 펄스)을 분리해 임계구역을 82 %
> 축소, 센서 판독 성공률 100 % 를 유지한 채 유실률을 0.039 % 로 낮춤."

## 5-g. CAN 버스 부하 실측 + 최악 응답시간 분석

§7 의 12.06 % 는 **계산값**이었다. 실측으로 검증하고, 거기서 나온 부하로
안전 신호의 최악 응답시간을 계산해 ID 재배치가 필요한지 판정했다.

### 측정 방법

각 노드의 프레임 카운터를 ST-Link 로 두 번 읽어 프레임/초를 구하고
DLC 별 프레임 비트수를 곱한다. **`tcpdump` 는 쓸 수 없다** — 그건 이더넷
UDP 를 잡는 도구이고 CAN 버스와 무관하다.

```
프레임 비트수 (Standard CAN 2.0A, N 데이터바이트)
  공칭 = 47 + 8N            SOF1 ID11 RTR1 IDE1 r0-1 DLC4 CRC15 CRCdel1 ACK2 EOF7 IFS3
  최악 = 공칭 + floor((33 + 8N) / 4)     비트스터핑 최대

  DLC1  공칭 55  최악 65        DLC2  공칭 63  최악 75        DLC8  공칭 111  최악 135
```

### 실측 결과 (창 90 초)

| 버스 | 보레이트 | 프레임/초 | 공칭 부하 | **최악 부하** |
|---|---|---|---|---|
| FRONT (H723 ↔ F407_Front) | 250 k | **402.5** | 9.55 % | **11.33 %** |
| REAR (H723 ↔ F446) | 250 k | **89.0** | 3.10 % | **3.74 %** |
| REAR (H723 ↔ RearBody) | 500 k | — | — | 측정 불가 (아래) |

**§7 의 계산값 12.06 % 는 옳았다.** 동일 조건으로 이론 사용률을 다시 계산하면
정확히 12.06 % 가 나오고, 실측 최악 11.33 % 가 이를 뒷받침한다.
실측이 6 % 낮은 것은 이벤트 트리거 적용 후 하행 명령이 변화 없을 때
하트비트 주기로만 나가기 때문이다.

**설계 상한 30~40 % 대비 3 배 이상 여유**가 있다.

### FRONT 버스 상위 부하 신호

| 신호 | DLC | Hz | 부하 |
|---|---|---|---|
| F446→H723 IMU `0x301` (REAR 버스) | 8 | 47.2 | 2.55 % |
| H723→F407 명령 `0x310`~`0x316` | 1 | 66.6 | 1.73 % |
| F407→H723 조향/브레이크/가속 `0x210~0x212` | 2 | 46.8 각 | 1.41 % 각 |
| F407→H723 액추에이터 위치 `0x21A` | 2 | 46.8 | 1.40 % |

### 최악 응답시간 — Tindell/Davis 분석

```
R_i = w_i + C_i
w_i = B_i + Σ_{j∈hp(i)} ceil((w_i + τ_bit) / T_j) × C_j
```

`B_i` 는 더 낮은 우선순위 프레임이 이미 송신 중일 때의 블로킹,
`hp(i)` 는 더 높은 우선순위(= 더 작은 ID) 메시지 집합.

| ID | 신호 | DLC | 주기 | **최악 응답** | 주기 대비 |
|---|---|---|---|---|---|
| `0x201` | 핑 (최고 우선순위) | 8 | 500 ms | **1,080 µs** | 0.2 % |
| `0x211` | **브레이크 ADC** | 2 | 20 ms | **1,680 µs** | 8.4 % |
| `0x212` | 가속 ADC | 2 | 20 ms | 1,980 µs | 9.9 % |
| `0x21A` | 액추에이터 위치 | 2 | 20 ms | 4,180 µs | 20.9 % |
| `0x310` | 조향 오버라이드 | 1 | 100 ms | 5,780 µs | 5.8 % |
| `0x316` | 방향지시 모드 (최저) | 1 | 100 ms | **7,080 µs** | 7.1 % |

### 결론 — ID 재배치는 하지 않는다

**최고 우선순위와 최저 우선순위의 차이가 1.08 ms → 7.08 ms, 즉 6 ms 다.**

방금 §5-c~§5-f 에서 제거한 지연은 **99~150 ms** 였다. ID 재배치로 얻을 수 있는
최대치는 그것의 **4 %** 이고, 모든 메시지가 이미 자기 주기의 21 % 안에
들어온다. 반면 비용은 보드 5 개 펌웨어 + ICD + Jetson 파서 동시 수정이다.

> **"측정했더니 바꿀 필요가 없었다"가 결론이고, 이것도 결과물이다.**
> 브레이크 ADC 는 이미 `0x211` 로 상위 우선순위이고 최악 1.68 ms 다.

**검토했다가 기각한 재배치안** — 브레이크등을 `0x322 → 0x301` 로 올리자는
제안이 있었으나 **`0x301` 은 F446 이 IMU 데이터로 쓰고 있고 램프 명령과
같은 버스**다. F446 필터가 `mask 0x0000`(전부 수신)이라 충돌 즉시 오동작한다.
또한 Front `0x310~0x316` 과 Rear `0x320~0x323` 은 **물리적으로 분리된 별개
버스**라 우선순위를 나란히 비교할 대상이 아니다.

## 5-h. `0x323` 고아 신호 — 아무도 받지 않는 명령 ★

`CAN_ICD.md` 에 미해결로 남겨뒀던 항목인데 **정적·동적 증거가 모두 나왔다.**

### 정적 증거

| 노드 | `0x323` 수신 여부 |
|---|---|
| RearBody_F407 | 필터가 `0x101` 단독 정확일치(`mask 0x7FF`) → **차단** |
| F446 (`Node_F447_Real`) | `0x320`/`0x321`/`0x322` 만 처리, `0x323` 분기 없음 → **무시** |

### 동적 증거 (창 180 초)

| 관측 | 값 |
|---|---|
| Rear H723 `0x323` 송신 | 1,824 프레임 (**10.1 Hz**) |
| F446 `can250_rx_bad_count` 증가 | 1,826 (**10.1 Hz**) |

**송신율과 불량 프레임 증가율이 완전히 일치한다.** 창문 명령이 하나도 빠짐없이
F446 의 "처리 못한 프레임" 카운터로 들어가고 있다.

### 두 가지 결함

1. **기능이 죽어 있다.** 창문 명령은 버스에 나가서 사라진다. Jetson 이 창문을
   조작해도 아무 일도 일어나지 않는다.
2. **진단 카운터를 오염시킨다.** `can250_rx_bad_count` 는 실제 CAN 이상을
   나타내야 하는데, 이 고아 신호가 10 Hz 로 채우고 있어 **진짜 불량 프레임이
   묻힌다.** 이 상태에서는 통신 이상을 카운터로 판별할 수 없다.

> 두 번째가 더 나쁘다. 죽은 기능은 안 쓰면 그만이지만, 못 쓰게 된 진단
> 카운터는 **다른 고장을 숨긴다.**

### 조치는 설계 판단이 필요하다

- (a) F446 에 `0x323` 수신·구동 추가 → 기능 복구
- (b) `0x323` 송신 제거 → 신호 폐기
- (c) F446 에 "알려진 무시 대상" 분기 추가 → 최소한 진단 오염만 제거

어느 쪽이든 신호 사양 변경이라 임의로 정하지 않았다.

## 5-i. 계획에 없던 실제 고장 — 진단 시스템 검증

측정 중 **RearBody_F407 이 리셋 상태로 붙들리는 고장**이 발생했다.
계획한 시험이 아니라 우연히 난 진짜 고장이다.

### 증상과 계측값

| 관측 지점 | 값 |
|---|---|
| RearBody SWD | `DEV_TARGET_HELD_UNDER_RESET`, Device ID `0x413` 은 응답 |
| RearBody 플래시 읽기 | 전부 `0x00000000` (지워진 플래시는 `0xFF` — 접근 실패라는 뜻) |
| Rear H723 `can500_tx_count` | 17 에서 정지 |
| Rear H723 `can500_tx_busy_count` | **1,548** 이후 계속 증가 (TX FIFO 포화) |
| FDCAN1 `TxErrorCnt` | **255** (최대) |
| FDCAN1 `BusOff` / `ErrorPassive` / `Warning` | **1 / 1 / 1** |

상대 노드가 ACK 를 주지 않으면 송신 오류 카운터가 255 까지 올라가 버스오프에
빠지고, `AutoRetransmission = ENABLE` 이라 TX FIFO 가 가득 찬 채로 남는다.

### 진단 시스템이 잡아냈다

```
[R] U0001  TEST_FAILED|CONFIRMED|WARNING   occ=1   검출 500ms
```

설계한 검출 시간 500 ms 대로 확정되고 `WARNING` 까지 올라갔다.
**계획하지 않은 실제 고장에서 진단 체인 전체(감지 → 디바운스 → 확정 →
경고 → UDP 보고 → Jetson 로깅)가 동작한 것**이 이 항목의 값어치다.

> **자소서 문장 예시**
> "시험 중 하위 제어기가 리셋 상태로 고착되는 실제 고장이 발생했고, 설계한
> 진단 시스템이 500 ms 만에 CAN 버스오프를 확정해 경고 등급으로 보고했다.
> ST-Link 로 상대 노드의 TxErrorCnt 255 / BusOff 세트와 자기 노드의 TX FIFO
> 포화를 함께 확인해, 증상과 진단 결과가 일치함을 검증했다."

**REAR 500 k 버스 부하는 이 고장 때문에 측정하지 못했다.** RearBody 복구 후
재측정이 필요하다.

## 5-j. `confirm_ms` 트레이드오프 — 검출 시간 vs 오검출 내성 ★

진단 디바운스 값을 얼마로 둘 것인가. 감으로 정하지 않고 스윕으로 결정했다.

### 재빌드 없이 스윕하기

`confirm_ms` 는 컴파일 상수라 값마다 재빌드·재플래시가 필요했다.
**진단 보정 테이블을 `const` 에서 RAM 으로 옮겨** 디버거로 써 넣을 수 있게 했다.

```c
/*
 * 진단 보정값(calibration). const 를 빼 RAM 에 두는 이유는 두 가지다.
 *  1) confirm_ms / heal_ms 는 차량마다 재조정 대상이다.
 *     양산 ECU 가 진단 보정값을 EEPROM 에 두는 것과 같은 취지.
 *  2) 값마다 재빌드하면 스윕 시험을 돌릴 수 없다.
 */
static diag_def_t front_dtc_defs[DTC_IDX_COUNT] = { ... };
```

`Diag_Init()` 이 배열을 복사하지 않고 포인터로 참조하므로 즉시 반영된다.
한 값당 재플래시 없이 `-w16` 한 번이면 된다.

### 시험 설계

무작위 손실률로는 표본이 모이지 않는다. 링크 타임아웃 500 ms 를 넘기려면
5회 연속 손실이 필요하고(p=0.5 에서 3 %), `500 + confirm_ms` 를 넘기려면
20회 연속이 필요해(p=0.5 에서 10⁻⁶) 사실상 관측되지 않는다.

그래서 **공백 길이 G 를 직접 만들어 넣고** 그것이 고장 선언으로 이어지는지
봤다. 각 시행: 6 초 정상 송신(치유) → G ms 송신 중단 → 4 초 관찰.

### 결과 — 임계가 정확히 `500 + confirm_ms` 를 따라간다

`TEST_FAILED` 발생 횟수 / 시행 횟수

| `confirm_ms` | 예상 임계 | 임계 아래 | 임계 아래 | 임계 위 | 임계 위 |
|---|---|---|---|---|---|
| 200 | 700 ms | 550: **0/2** | — | 850: **2/2** | 1100: **2/2** |
| 500 | 1000 ms | 600: **0/2** | 850: **0/2** | 1150: **2/2** | 1400: **2/2** |
| 1000 | 1500 ms | 1100: **0/2** | 1350: **0/2** | 1650: **2/2** | 1900: **2/2** |
| 1500 | 2000 ms | 1600: **0/2** | 1850: **0/2** | 2150: **2/2** | 2400: **2/2** |
| 2000 | 2500 ms | 2100: **0/2** | 2350: **0/2** | 2650: **2/2** | 2900: **2/2** |

**10 배 범위(200~2000 ms)에서 예외 없이 일치한다.**

### 반대편 — 검출 시간도 같은 값을 따른다

| `confirm_ms` | 설계 검출시간 | 호스트 실측 |
|---|---|---|
| 500 | 1000 ms | 937.2 ms |
| 1000 | 1500 ms | 1448.2 ms |
| 1500 | 2000 ms | 1931.7 ms |

(실측이 60~70 ms 짧은 것은 §5 에 적은 주입기 타임스탬프 편향이다.)

### 결론 — 공짜가 없다

```
오검출 내성 임계  =  검출 시간  =  링크 타임아웃 + confirm_ms
```

**두 값이 같은 수식이다.** 검출을 빠르게 하면 그만큼 짧은 글리치에도
고장을 선언하고, 글리치에 둔감하게 하면 그만큼 검출이 느려진다.
1:1 교환이라 "둘 다 좋게" 하는 튜닝은 존재하지 않는다.

**따라서 `confirm_ms` 는 성능 목표가 아니라 "견뎌야 할 최대 통신 공백"이
정한다.** 그 값을 정하면 검출 시간은 자동으로 결정된다.

### 이 시스템에서의 판단

측정된 링크 품질은 **2000/2000 무손실, RTT p99 0.663 ms** 다(§5-b).
글리치 근거가 관측되지 않으므로 `confirm_ms` 를 더 줄일 여지가 있다.
현재 1500 ms 는 **2 초짜리 통신 두절까지 흡수**하는 설정이고,
케이블 재삽입·스위치 재수렴 같은 실사용 상황을 감안한 여유로 유지한다.

> **자소서 문장 예시**
> "진단 디바운스 값을 감으로 정하지 않기 위해 보정 테이블을 RAM 으로 옮겨
> 재빌드 없이 스윕할 수 있게 만들고, 통신 공백 길이를 제어해 오검출 임계를
> 실측했다. 200~2000 ms 전 범위에서 오검출 임계와 검출 시간이 모두
> `링크 타임아웃 + confirm_ms` 로 일치함을 확인해, 두 지표가 1:1 교환 관계라
> 동시 최적화가 불가능함을 정량적으로 보였다. 따라서 이 값은 성능 목표가
> 아니라 견뎌야 할 최대 통신 공백에서 역산해야 한다고 결론지었다."

### 계측 도구에서 잡은 오류 네 가지

스윕이 처음에 전부 0 으로 나왔고, 원인이 전부 **내 측정 코드**에 있었다.

| 오류 | 증상 | 교훈 |
|---|---|---|
| `STM32_Programmer_CLI -w16` 에 10진수 전달 | 값이 `0` 으로 써짐 | write 후 **읽어서 확인**한다 |
| `ENTRY_FMT` 를 기억으로 작성 (`<HHBBIIHH`) | 필드가 밀려 코드 불일치 | 동작하는 파서에서 **복사**한다 |
| U0300 코드를 `0x0300` 으로 검색 | 실제는 `0xC300` (J2012 에서 U = 상위 2비트 `0b11`) | 메모리 덤프에서 이미 봤는데 반영 안 함 |
| `CONFIRMED` 를 현재 상태로 사용 | 비트값도 틀렸고(4 인데 8), **ISO 14229 상 래치**라 과거 이력으로 계속 서 있음 | 현재 상태는 `TEST_FAILED` 로 본다 |

> 마지막 것이 가장 중요하다. `CONFIRMED` 는 정비사가 지울 때까지 남는
> **이력**이고, 지금 고장인지는 `TEST_FAILED` 가 나타낸다. 표준을 따라
> 구현해 놓고 정작 측정할 때 그 의미를 잘못 썼다.

## 5-k. 진단 판정 기준이 틀려 실제 고장을 놓쳤다 ★★

§5-i 에서 "진단이 실제 고장을 잡았다"고 썼는데, **같은 고장의 다른 국면에서는
놓치는 것**을 이어서 발견했다. 이쪽이 훨씬 중요한 발견이다.

### 관측 — 링크가 죽었는데 시스템은 정상이라고 보고

RearBody 가 리셋 고착에서 복귀해 정상 실행 중인데도 500 k 링크가 살아나지
않았다. 그 상태에서 계측한 값이다.

| 관측 | 값 |
|---|---|
| RearBody 실행 | **정상** (`uwTick` 5 초에 5,362 증가) |
| RearBody 펌웨어 | ELF 와 sha256 일치 |
| Rear H723 `can500_tx_count` | **8 에서 정지** (60 초간 증가 0) |
| Rear H723 `can500_rx_count` | **0** |
| Rear H723 `can500_tx_busy_count` | 60 초에 **+125** (TX FIFO 포화) |
| FDCAN1 `TxErrorCnt` | **128** (에러 패시브 문턱에 고정) |
| FDCAN1 `ErrorPassive` / `Warning` | **1 / 1** |
| FDCAN1 `BusOff` | **0** |
| **DTC `U0001`** | **클리어 — 정상으로 보고** |
| 대조군: 250 k 버스 | 30 초에 +2,490 프레임 (정상) |

### 원인 — CAN 규격의 TEC 예외 조항

판정 기준이 `BusOff` 하나였다.

```c
Diag_Report(DTC_IDX_CAN500_BUSOFF,
            (can500_protocol_status.BusOff != 0U) ? 1U : 0U, now);
```

그런데 CAN 규격에는 **"에러 패시브 송신기가 ACK 오류를 검출했고 그동안
dominant 비트를 보지 못했다면 TEC 를 증가시키지 않는다"** 는 예외가 있다.

상대 노드가 그냥 사라지면 ACK 를 주는 노드가 없으므로 이 예외에 걸린다.
TEC 는 **128 에서 멈추고 버스오프(TEC > 255)에 영원히 도달하지 않는다.**
실측한 `TxErrorCnt = 128` 이 정확히 그 값이다.

> **"버스오프 = CAN 고장"이라는 통념이 틀렸다.**
> 버스오프는 *시끄러운* 버스에서 생기고, *조용한* 버스(상대 소실)에서는
> 에러 패시브에 머문다. 후자가 더 흔한 고장 형태인데 그걸 놓치고 있었다.

§5-i 에서 `U0001` 이 떴던 것은 RearBody 가 리셋에 붙들려 있던 국면에서
버스에 dominant 비트가 있어 TEC 가 255 까지 갔기 때문이다. **같은 물리 고장이
국면에 따라 검출되기도 하고 안 되기도 했다.**

### 수정 — 수신 두절을 함께 본다

이더넷 링크(`U0100`/`U0300`)가 이미 쓰던 판정 방식과 같게 맞췄다.

```c
#define CAN_RX_TIMEOUT_MS      2000U   /* 핑 주기 500 ms 의 4배 */
#define CAN_STARTUP_GRACE_MS   3000U

static uint8_t CAN_LinkDead(uint32_t now, uint8_t busoff,
                            uint32_t rx_count, uint32_t last_rx_tick)
{
    if (busoff != 0U)      { return 1U; }
    if (rx_count == 0U)    { return (now > CAN_STARTUP_GRACE_MS) ? 1U : 0U; }
    if ((int32_t)(now - last_rx_tick) < 0) { return 0U; }   /* ISR 이 방금 갱신 */
    return ((uint32_t)(now - last_rx_tick) > CAN_RX_TIMEOUT_MS) ? 1U : 0U;
}
```

수신 시각을 남기려고 RX 콜백에 `can500_last_rx_tick` / `can250_last_rx_tick`
갱신을 추가했다. 부호 있는 비교는 §4 의 언더플로우 교훈을 그대로 적용한 것이다.

### 결과

| | 개선 전 | 개선 후 |
|---|---|---|
| 링크 상태 | 완전 두절 (tx 0 / rx 0, 2분 이상) | 동일 |
| **DTC `U0001`** | **클리어 (정상 보고)** | **`TEST_FAILED\\|CONFIRMED\\|WARNING`** |
| 검출 시간 | **검출 불가** | **500 ms** |
| 정상 버스(250 k) 오검출 | — | **없음** |

> **자소서 문장 예시**
> "하위 제어기가 살아 돌아왔는데도 CAN 링크가 복구되지 않는 것을 계측하다,
> 진단 시스템이 이 고장을 전혀 보고하지 않는 것을 발견했다. 판정 기준이
> 버스오프 단독이었는데, CAN 규격상 에러 패시브 송신기는 ACK 오류로 TEC 를
> 올리지 않아 상대 노드가 소실된 경우 버스오프에 도달하지 않는다.
> `TxErrorCnt=128 / BusOff=0` 인 채 링크가 죽어 있음을 레지스터로 확인하고,
> 수신 두절 기반 판정을 추가해 검출 불가였던 고장을 500 ms 검출로 개선했다."

### 함께 추가한 것 — 버스오프 자동 복구

FDCAN 은 버스오프에 빠지면 하드웨어가 `CCCR.INIT` 을 세우고 그대로 멈춘다.
소프트웨어가 `INIT` 을 내려야 표준 복구 시퀀스(129 × 11 recessive bit)가
시작되는데, **그 코드가 없었다.** `HAL_FDCAN_Start()` 는 초기화 때 한 번뿐이다.

```c
static void CAN_BusOffRecover(uint32_t now)
{
    if (can500_protocol_status.BusOff != 0U) {
        if ((uint32_t)(now - can500_last_try) >= CAN_BUSOFF_RECOVER_MS) {
            can500_last_try = now;
            CLEAR_BIT(hfdcan1.Instance->CCCR, FDCAN_CCCR_INIT);
            can500_busoff_recover_count++;
        }
    }
    /* CAN250 도 동일 */
}
```

재시도 간격 1 초를 두는 이유는, 배선이 끊긴 채로 두면 복구 → 즉시 버스오프를
반복하며 버스를 흔들기 때문이다.

이더넷의 "리셋해야 산다"(§1), RearBody 의 `AutoBusOff = DISABLE`(§8) 과
**같은 계열의 결함**이다. 셋 다 "고장을 감지는 하는데 빠져나올 길이 없다".

### 남은 것 — 500 k 배선은 물리 고장

이 수정으로 **검출**은 되지만 링크 자체는 아직 죽어 있다. 두 노드 모두
정상 실행 중이고 250 k 버스는 멀쩡한데 500 k 만 무통신이므로,
`FDCAN1 ↔ RearBody CAN1` 구간의 배선·종단저항·트랜시버 확인이 필요하다.

## 6-b. FreeRTOS 전환 — 성능이 아니라 구조 ★

### 전제: 성능 개선을 목표로 하지 않았다

§6 의 baseline 이 그 이유다. 슈퍼루프는 이미 결정적이고 CAN 은 ISR 기반이라
**응답성에서 얻을 것이 없다.** 오늘 제거한 99~150 ms 지연도 전부 *주기 전송
구조* 탓이었지 스케줄링 탓이 아니었다.

그래서 목표를 **구조**로 잡았다 — 기능별 태스크 분리, 우선순위로 표현되는
중요도, 기능 추가 시 다른 기능의 주기에 영향을 주지 않는 것.
**측정의 목적도 "개선 입증"이 아니라 "회귀 없음 확인"이다.**

### CubeMX 를 쓰지 않았다

CubeMX 는 FreeRTOS 를 켜면 **lwIP 를 `NO_SYS=0` 으로 강제 전환**한다.
그러면 캐시 ECC(§1) / D2 SRAM 클럭 / MPU / PHY 타이밍까지 하루 걸려 안정화한
이더넷 통합을 전부 다시 만들어야 한다.

손으로 통합해 **`NO_SYS=1` 을 유지**했다. 대신 제약이 하나 생긴다 —
**단 하나의 태스크만 lwIP 를 만질 수 있다.** 텔레메트리·진단 송신을 전부
NET 태스크에 몰아넣은 이유다.

타임베이스도 CubeMX 기본(HAL=TIM6, FreeRTOS=SysTick)을 따르지 않았다.
코드 전체가 `HAL_GetTick()` 기준으로 주기를 재고 있어 의미를 바꾸고 싶지
않았다. SysTick 하나를 둘이 쓰되 스케줄러가 뜬 뒤에만 커널 틱을 돌린다.

```c
void SysTick_Handler(void)
{
  HAL_IncTick();
  if (xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED)
  {
      xPortSysTickHandler();
  }
}
```

### 1차 시도 — 둘 다 1 ms 주기 폴링. 실패했다

가장 평범한 구성으로 시작했다. CTRL(prio 3) / NET(prio 2), 둘 다
`vTaskDelayUntil` 1 ms.

**태스크 주기 자체는 훌륭했다.**

| 태스크 | 최소 | 최대 | 평균 | 표본 |
|---|---|---|---|---|
| CTRL | 981 µs | 1,018 µs | 999 µs | 59,854 |
| NET | 974 µs | 1,022 µs | 999 µs | 60,484 |

**지터 ±25 µs.** 주기 정확도만 보면 슈퍼루프보다 낫다.

**그런데 지연이 무너졌다.**

| | 슈퍼루프 | RTOS 1 ms 폴링 |
|---|---|---|
| ACK RTT p50 | 0.239 ms | **0.874 ms** |
| 하행 명령 최대 | 175 µs | **4,014 µs** |
| 하행 명령 1 ms 초과 | 0 / 302 | **15 / 302** |

원인은 명확했다. **이 프로젝트의 lwIP 는 인터럽트를 쓰지 않는다** —
`ethernetif_input()` 이 DMA 디스크립터를 폴링하는 완전 폴링 구조다.
슈퍼루프는 이걸 38 kHz 로 돌렸는데 1 ms 태스크는 1 kHz 로 떨어뜨린다.
**폴링 빈도가 곧 지연이 된다.**

### 2차 — 이벤트 구동으로 되찾았다

ETH 인터럽트를 새로 켜는 것은 겨우 안정화한 이더넷 경로를 다시 건드리는
일이라 피했다. 대신 **RTOS 구조 자체로** 해결했다.

```
NET (prio 1)   최저 우선순위 배경 폴링. 블로킹하지 않는다.
               남는 CPU 를 전부 lwIP 폴링에 쓴다.
CTRL (prio 3)  알림 기반. 지령이 바뀌면 NET 이 즉시 깨운다.
               깨울 일이 없으면 1 ms 하트비트.
```

```c
/* NET: 지령이 바뀌면 CTRL 을 즉시 깨운다. 지령은 UDP 로 들어오므로
   NET 이 가장 먼저 안다. */
if ((changed != 0U) && (h_task_ctrl != NULL)) { (void)xTaskNotifyGive(h_task_ctrl); }

/* CTRL: 알림이 오면 즉시, 없으면 1 ms 하트비트로 깨어난다. */
(void)ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(TASK_CTRL_PERIOD_MS));
```

**우선순위 역전처럼 보이지만 아니다.** CTRL 이 준비되면 언제든 NET 을
선점하므로 제어 결정성은 유지되고, 그 외 시간은 전부 lwIP 가 쓴다.
베어메탈의 폴링 속도를 되찾으면서 우선순위 구조는 그대로 남는다.

### 같은 조건 A/B — 회귀 없음

앞선 비교는 몇 시간 전 베이스라인과 대조한 것이라 공정하지 않았다.
**보관해 둔 슈퍼루프 ELF 를 다시 구워 같은 조건에서 재측정**했다.

| 항목 | 슈퍼루프 | RTOS (이벤트 구동) | 판정 |
|---|---|---|---|
| ACK RTT p50 | 0.251 ms | **0.247~0.257 ms** | 동등 |
| ACK RTT p99 | 0.975 ms | 1.17~1.77 ms | 약간 나쁨 |
| 폴링 주기 평균 | 72 µs | **55 µs** | RTOS 가 빠름 |
| 폴링 주기 최대 | 539 µs | **531 µs** | 동등 |
| 하행 명령 평균 | 29 µs | **31 µs** | 동등 |
| **하행 명령 최대** | **79 µs** | **759 µs** | **10배 나쁨** |
| 하행 명령 1 ms 초과 | 0 / 302 | **0 / 302** | 동등 |
| 종단 반영 평균 | 6,911 µs | **6,222 µs** | 동등 |
| 종단 반영 최대 | 29,791 µs | **26,568 µs** | 동등 |

**평균은 전부 동등하고, 최악값만 명령 경로에서 10배 나빠졌다**(79 → 759 µs).
그래도 서브밀리초이고 1 ms 초과는 0 회다.

폴링 주기가 오히려 빨라진 것(72 → 55 µs)은 NET 태스크에서 CAN 작업이
빠져나갔기 때문이다. **기능을 분리한 효과가 수치로 나타난 것**이다.

### 대조군이 잘못된 결론을 막았다

RTOS 판에서 ACK RTT 꼬리(p99 1.8 ms)가 보여 "RTOS 오버헤드"로 결론지을 뻔했다.
**손대지 않은 Rear(슈퍼루프)를 같이 재보니 같은 꼬리가 있었다.**

```
Front (RTOS)      min 0.187 / avg 0.512 / max 1.029 ms
Rear  (슈퍼루프)   min 0.257 / avg 0.698 / max 1.043 ms   <- 대조군
```

오히려 Front 가 빨랐다. **꼬리는 RTOS 가 아니라 측정 환경 변화였다.**
초기 베이스라인(p99 0.663)은 몇 시간 전 조건에서 잰 값이다.

> 이더넷 추적(§DEBUG_JOURNAL 5.3)에서 배운 "대조군을 유지한다"가 여기서
> 그대로 값을 했다. 대조군이 없었으면 RTOS 를 잘못 기소했을 것이다.

> RTOS 원인이 아닌 환경 요인임을 분리했다."

## 6-c. Rear FreeRTOS 전환 — CubeMX 정식 경로 (`NO_SYS=0`) ★★

Front 는 손으로 통합해 `NO_SYS=1` 을 유지했다(§6-b). Rear 는 **CubeMX 로
정식 전환**해 `NO_SYS=0` 까지 갔다. 두 방식을 비교할 수 있게 된 셈이다.

| | Front (§6-b) | **Rear (이 절)** |
|---|---|---|
| 통합 방식 | 손으로 | **CubeMX 생성** |
| lwIP | `NO_SYS=1` 유지 | **`NO_SYS=0`** |
| lwIP 구동 | 태스크가 폴링 | **전용 `tcpip` 스레드** |
| 수신 | DMA 디스크립터 폴링 | **ETH ISR → 세마포어** |
| 현재 상태 | 롤백됨 | **적용 중** |

### 구성

| 항목 | 값 |
|---|---|
| 커널 | FreeRTOS + CMSIS-RTOS v2, heap_4 |
| 힙 | **48,000 B** |

### 겪은 문제 네 가지 — 전부 `NO_SYS` 전환의 구조적 결과

CubeMX 가 코드를 잘못 만든 게 아니다. **실행 모델이 바뀌면서 따라온 것**이다.

#### ① `ethernetif.c` 재생성으로 GPIO 속도 소실

`NO_SYS=0` 은 `ethernetif.c` 를 **구조째 다시 만든다**(세마포어 + 전용 수신
스레드). RMII 핀 4곳의 `GPIO_SPEED_FREQ_VERY_HIGH` 가 `HIGH` 로 되돌아갔다.

> 이 파일은 생성 코드라 `USER CODE` 보호를 못 받는다. 재생성 때마다 확인해야 한다.

#### ② PHY 안정화 지연 소실 — 사용자 마커의 함정

`USER CODE BEGIN PHY_SETTLE` 라는 **직접 만든 마커**에 넣어 뒀는데,
CubeMX 가 모르는 이름이라 **블록째 사라졌다.**

```c
/* 복원: 기본 태스크의 lwIP 초기화 직전으로 옮김 */
osDelay(500);        /* HAL_Delay -> osDelay (태스크 문맥) */
MX_LWIP_Init();
```

> **교훈**: CubeMX 가 생성하는 마커 이름만 신뢰할 수 있다. 임의 마커는 보호받지 못한다.

#### ③ `MX_LWIP_Process()` 가 사라짐

```
NO_SYS=1   메인루프가 MX_LWIP_Process() 를 폴링
NO_SYS=0   lwIP 가 자기 tcpip 스레드로 스스로 돎  ->  폴링 함수 자체가 없음
```

컴파일 에러(`implicit declaration`)로 바로 드러나 찾기 쉬웠다.
슈퍼루프 본문을 `Rear_AppStep()` 으로 옮기고 이 호출만 제거했다.

#### ④ 초기화 순서 역전 → **폴트 없이 전체 정지** ★

가장 찾기 어려웠다.

```
NO_SYS=1   main()  : MX_LWIP_Init()  ->  RearZoneNetwork_Init()  (UDP 소켓 생성)
NO_SYS=0   main()  : RearZoneNetwork_Init()   <- lwIP 아직 초기화 안 됨!
           task    : MX_LWIP_Init()
```

`MX_LWIP_Init()` 이 기본 태스크로 옮겨가면서 **UDP 서버 개설이 lwIP 보다
먼저 실행**됐다. `udp_new()` 가 실패 → `Error_Handler()` →
`__disable_irq(); while(1);` → 시스템 정지.

**증상이 고약했다.**

| 관측 | 값 |
|---|---|
| `CFSR` / `HFSR` | **0 / 0** — 크래시가 아님 |
| `uwTick` | **0 에서 정지** |
| CAN·텔레메트리 카운터 | 전부 **0** |

폴트가 없으니 스택 추적이 무의미하다. `Error_Handler()` 가 인터럽트를 끄는
구조라는 걸 알고 **"어디서 그게 불렸나"를 역추적**해야 했다.

```c
/* 조치: lwIP 의존 초기화를 태스크로 이동 */
MX_LWIP_Init();
if (RearZoneNetwork_Init() != ERR_OK) { Error_Handler(); }
if (RearTelemetry_Init()  != ERR_OK) { Error_Handler(); }
```

> **일반화하면** — RTOS 전환은 코드를 옮기는 일이 아니라 **초기화 순서와
> 실행 문맥을 재배치**하는 일이다. "무엇이 무엇보다 먼저 준비돼야 하는가"가
> 바뀌는데, 컴파일러는 그걸 잡아주지 않는다.

## 6-d. 태스크 분리와 디스패치 방식 — A/B/C 실측 비교 ★★

Rear 를 기능별 태스크로 나누고, **젯슨이 장애물을 감지해 브레이크를 거는
경로**의 지연을 세 가지 설계로 비교했다.

### 태스크 구성

나누는 기준은 신호 개수가 아니라 셋이다 — **타이밍 등급 / 블로킹 여부 /
자원 소유권**. 신호는 18 개지만 태스크는 4 개다.

| 태스크 | 담당 | 주기 | 우선순위 |
|---|---|---|---|
| `EthIf` | ETH 수신 (CubeMX 생성) | 세마포어 | 최고 |
| **`WHEEL`** | 500 k 버스 (바퀴값 자리) | 10 ms | 27 |
| **`CTRL`** | 250 k 램프·윈도우, CAN 진단·버스오프 복구 | 10 ms | 25 |
| `tcpip` | lwIP 코어 + UDP 수신 콜백 | — | 24 |
| **`NET`** | 텔레메트리·perf·DTC 송신 (lwIP 독점) | 20 ms | 23 |
| **`DIAG`** | DTC 판정 | 50 ms | 22 |

**CAN 수신은 태스크가 없다.** ISR 이 7~13 µs 에 처리하므로 태스크로 옮기면
문맥전환만 더해져 느려진다. `tcpip` 를 기준선으로 위아래에 배치했다.

측정된 태스크 주기 — 지터가 작다.

| 태스크 | 최소 | 최대 | 평균 | 설정 |
|---|---|---|---|---|
| `WHEEL` | 9,477 | 10,072 | **9,999** | 10 ms |
| `CTRL` | 9,429 | 10,072 | **9,999** | 10 ms |
| `NET` | 19,255 | 20,444 | **19,997** | 20 ms |
| `DIAG` | 49,176 | 50,327 | **49,997** | 50 ms |

---

### 브레이크 디스패치 A/B/C — 각 200 표본

```
Jetson -> ETH ISR -> EthIf -> tcpip(콜백에서 변수 갱신) -> ??? -> CAN 0x322
                                                           ^^^
                                                      여기만 바꿨다
```

| | **A 주기 폴링** | **B 알림** | **C 전용 태스크** |
|---|---|---|---|
| 최소 | 60 µs | 18 µs | **12 µs** |
| **평균** | **4,308 µs** | **47 µs** | **13 µs** |
| **최대** | **9,981 µs** | 201 µs | **15 µs** |
| 산포 (max−min) | 9,921 µs | 183 µs | **3 µs** |
| 태스크 수 | 4 | 4 | 5 |
| FDCAN2 접근 태스크 | 1 | 1 | **2 → 락 필요** |

**A → B 는 91 배, B → C 는 3.6 배.**

- **A** 의 평균 4,308 µs ≈ 10 ms 주기의 절반, 최대 9,981 µs ≈ 주기 전체.
  **0~10 ms 균등분포**의 교과서적 형태다.
- **B** 는 `CTRL` 주기 최소가 187 µs 로 찍혔다 — 알림으로 조기 기동한 흔적.
  다만 `CTRL` 이 CAN 진단·핑·UDP 적용을 먼저 거친 뒤 브레이크를 보내 47 µs.
- **C** 는 12~15 µs, 산포 3 µs. 거의 문맥전환 시간 그 자체다.

### C 의 대가 — 락이 필요해진다

`CTRL` 과 `BRAKE` 가 둘 다 FDCAN2 TX FIFO 를 만진다.
`HAL_FDCAN_AddMessageToTxFifoQ()` 는 재진입 안전하지 않다.

락을 넣고 재측정하니 **13 → 23 µs (+10 µs)** 였다. 락 자체의 비용이다.

---

### 우선순위 역전 재현과 해소 ★★

락을 넣었으니 **뮤텍스 종류에 따른 차이**를 실험했다.
Mars Pathfinder 를 멈추게 한 그 문제다.

#### 실험 설계 — 역전을 확정적으로 만든다

우연히 겹치기를 기다리면 재현되지 않는다(1 차 시도에서 차이가 240 µs 에
그쳤다). 그래서 `HOG` 가 락을 잡은 직후 **스스로 나머지를 깨워** 세 태스크가
반드시 얽히게 했다.

```
HOG(22)    락 획득 → BRAKE 깨움 → NOISE 깨움 → 2 ms 점유 → 해제
BRAKE(26)  깨어나 락 요구 → HOG 가 쥐고 있어 대기
NOISE(24)  깨어나 5 ms 소모.  락과 무관하지만 HOG 를 선점한다
```

> **알림 순서가 결정적이었다.** `NOISE` 를 먼저 깨우면 그게 다 소모된 뒤에야
> `BRAKE` 가 막히므로 방해물이 남지 않는다. `BRAKE` → `NOISE` 순이어야
> 역전이 성립한다. 이 순서를 바꾸기 전에는 두 조건 모두 2 ms 로 같았다.

#### 결과 — 같은 부하, 락 종류만 다름

| | **이진 세마포어 (상속 X)** | **뮤텍스 (상속 O)** |
|---|---|---|
| 브레이크 지연 최소 | 7,080 µs | **2,059 µs** |
| **브레이크 지연 평균** | **7,096 µs** | **2,068 µs** |
| 브레이크 지연 최대 | 7,351 µs | **2,127 µs** |
| 락 대기 최대 | 7,330 µs | **2,108 µs** |
| 표본 | 1,063 | 1,525 |

**3.4 배 차이. 그리고 수치가 이론과 정확히 맞는다.**

```
상속 X :  NOISE 5 ms + HOG 2 ms = 7 ms      실측 7,096 µs
상속 O :  HOG 가 26 으로 승격 → NOISE(24) 가 선점 못 함 → 2 ms
                                             실측 2,068 µs
```

`BRAKE` 는 **가장 높은 우선순위인데 중간 우선순위 태스크 때문에 5 ms 를
더 기다린다.** 이게 우선순위 역전이고, 상속이 그 5 ms 를 없앤다.

> **CMSIS-RTOS2 의 `osMutexNew()` 는 기본으로 상속을 켠다.**
> (`cmsis_os2.c`: *"Priority inherit protocol is used by default"*)
> 반면 `osSemaphoreNew(1,1)` 로 상호배제를 구현하면 상속이 없다.
> **"뮤텍스와 세마포어의 차이"가 여기서 숫자로 드러난다.**

### 판단

| 설계 | 브레이크 지연 | 대가 |
|---|---|---|
| B (알림) | 47 µs | 없음 |
| C (전용 태스크 + 뮤텍스) | 23 µs | 락 1 개, 태스크 1 개, RAM 1 KB |

**34 µs 차이다.** 전체 경로에서 네트워크 전송만 약 250 µs 이므로 **13 %** 이고,
차량 동역학 기준으로는 의미가 없다.

**다만 세 수치를 모두 갖고 있다는 것이 핵심이다.** 더 빠른 설계를 알면서도
택하지 않은 이유를 숫자로 말할 수 있다.

> **자소서 문장 예시**
> "젯슨이 장애물을 감지해 브레이크를 거는 경로의 지연을 세 가지 디스패치
> 설계로 실측 비교했다. 주기 폴링 4,308 µs → 태스크 알림 47 µs → 전용 태스크
> 13 µs 로 91 배·3.6 배 개선되나, 전용 태스크는 CAN 페리퍼럴을 두 태스크가
> 공유해 뮤텍스가 필요해진다. 그 상태에서 우선순위 역전을 확정적으로 재현해
> 상속 없는 이진 세마포어는 7,096 µs, 상속 있는 뮤텍스는 2,068 µs 임을
> 측정했다. 최종적으로는 34 µs 이득을 위해 락과 태스크를 추가할 값어치가
> 없다고 판단하고 알림 방식을 택했다."

## 6-e. Front FreeRTOS 전환 — 그리고 "assert 가 가리킨 곳은 범인이 아니었다" ★★★

Rear 와 같은 절차(CubeMX + `NO_SYS=0`)로 Front 를 전환했다. 빌드도 되고
링크도 됐는데 **보드가 응답하지 않았다.** 원인을 찾는 과정이 이 절의 내용이다.

### 태스크 구성 (Front)

| 태스크 | 우선순위 | 주기 | 역할 |
|---|---|---|---|
| `EthIf` | 실시간(48) | 이벤트 | ETH RX 세마포어 대기 (CubeMX) |
| `tcpip_thread` | 24 | 이벤트 | lwIP 코어 (CubeMX) |
| `ctrl` | 25 | 10 ms + 알림 | FDCAN2 하행 명령 7종, CAN 진단·버스오프 복구 |
| `net` | 23 | 20 ms | 텔레메트리 SV / perf / DTC 송신, 존간 FRONT_STATE |
| `diag` | 22 | 50 ms | DTC 판정 5종, 스택·힙 여유 기록 |
| `defaultTask` | 24 | 초기화 후 유휴 | PHY 지연 500 ms → `MX_LWIP_Init()` → UDP 개설 → 태스크 기동 |

Rear 와 달리 `wheel` 이 없다. Front 는 CAN 버스가 FDCAN2 하나뿐이라 `ctrl` 이
독점하면 되고, 그 결과 **CAN 락이 필요 없다**(§6-d 의 C 안이 안고 있던 대가가
Front 에는 애초에 없다).

### 증상

```
ping 172.30.1.201        0/20   (100 % 손실)
CFSR / HFSR              0x00000000 / 0x00000000   <- 폴트 아님
gnetif ip                172.30.1.201              <- IP 정상
태스크 핸들 3개          전부 non-NULL             <- 생성 성공
xTickCount               1721 -> 1721 (5 초간 +0)  <- 커널 자체가 정지
uwTick                   1722
pxCurrentTCB             "tcpip_thread"
can250_rx_count=615  front_command_tx_count=86     <- 잠깐은 돌았다
```

폴트가 아니고, 틱과 `uwTick` 이 **같은 순간** 멈췄다. `configASSERT` 나
`Error_Handler` 의 `taskDISABLE_INTERRUPTS(); for(;;);` 에 빠진 모양이다.
그런데 CubeMX 기본 `configASSERT` 는 그냥 멈추기만 해서 **어디서 걸렸는지
알 수 없다.**

### 1단계 — assert 에 위치를 기록시켰다

```c
/* 원래: #define configASSERT(x) if((x)==0){taskDISABLE_INTERRUPTS(); for(;;);} */
void vAssertRecord(const char *file, int line);
#define configASSERT( x )  if ((x) == 0) { vAssertRecord(__FILE__, __LINE__); }
```

`LWIP_PLATFORM_ASSERT` 도 같은 함수로 돌렸다. ST-Link 로 변수를 읽으니:

```
file = ../Middlewares/Third_Party/LwIP/src/core/mem.c
line = 639   ->  LWIP_MEM_ILLEGAL_FREE("mem_free: illegal memory: double free")
```

### 2단계 — lwIP 이중 해제. 진짜 결함을 하나 찾았다

앱 콜백을 전부 확인했지만 경로마다 `pbuf_free()` 는 정확히 한 번이었다.
이중 해제는 **경쟁**이었다.

`NO_SYS=1`(폴링) 에서는 lwIP 를 만지는 문맥이 하나뿐이라 문제가 없었다.
`NO_SYS=0` 으로 바꾸는 순간 `tcpip_thread` 가 생기고, 내 `net` 태스크가
`udp_sendto()` 를 부르면 **두 문맥이 같은 ARP 큐를 만진다.** 한쪽이 큐에
넣은 pbuf 를 다른 쪽 `etharp_cleanup_netif()` 가 해제하면 그대로 이중 해제다.

lwIP raw API 는 스레드 안전하지 않다. 규정된 방법은 코어 락이다.

```c
LOCK_TCPIP_CORE();
FrontZoneNetwork_Process(now);   /* udp_send() 를 포함 */
UNLOCK_TCPIP_CORE();
```

Front 의 `net` 태스크 5 곳, `defaultTask` 의 UDP 개설 1 곳에 적용했다.
**Rear 도 같은 잠복 결함을 갖고 있어서** `Task_Ctrl` / `Task_Net` 양쪽에
동일하게 적용했다(Rear 는 아직 터지지 않았을 뿐이다).

### 3단계 — 증상만 옮겨갔다

```
file = FreeRTOS/Source/queue.c
line = 1278  ->  configASSERT( pxQueue->uxItemSize == 0 )   (xQueueGiveFromISR)
생존 시간   1721 틱 -> 6083 틱
ft_tx_count    1 -> 44
```

더 오래 살고 텔레메트리도 나갔지만 여전히 죽었다. 그리고 이번 assert 는
**말이 안 되는 내용**이었다 — ISR 이 세마포어를 주는데 그 객체가 세마포어가
아니라고 한다. 코드는 CubeMX 생성분 그대로이고 Rear 와 같다.

객체가 깨졌다는 뜻이다. 여기서 방향을 바꿨다. **assert 를 더 쫓지 않고,
조용히 지나가고 있던 훅부터 켰다.**

### 4단계 — 훅을 켜자 한 줄로 나왔다

`configCHECK_FOR_STACK_OVERFLOW` 는 이미 **2** 였다. 그런데 CubeMX 가 만든
`vApplicationStackOverflowHook()` 은 **본문이 비어 있었다.** 감지는 하고
있었지만 아무것도 안 하고 되돌아가 계속 망가진 채로 달리고 있었다.
`vApplicationMallocFailedHook()` 도 마찬가지였다.

둘 다 기록하고 멈추게 바꾸자:

```
overflow count = 1
overflow task  = EthIf        <- 범인
```

### 근본 원인 — 바이트인가 워드인가

```c
/* CubeMX 생성값 */
#define INTERFACE_THREAD_STACK_SIZE ( 350 )
attributes.stack_size = INTERFACE_THREAD_STACK_SIZE;
```

**CMSIS-RTOS v2 의 `stack_size` 단위는 워드가 아니라 바이트다.**
350 은 350 바이트, 곧 87 워드다. `ethernetif_input()` → `netif->input()`
경로가 이 안에 들어가지 않는다.

넘친 스택은 `heap_4` 의 인접 블록을 덮어썼다. 그래서 죽는 자리가
`mem.c` 였다가 `queue.c` 였다가 한 것이다. **앞의 두 assert 는 원인이 아니라
오염의 결과였다.**

### 실측 — 얼마나 모자랐나

`INCLUDE_xTaskGetHandle` 을 켜고 이름으로 조회해 최고수위(high water mark)를 쟀다.

| 스레드 | 할당 | 여유 | 실사용 최대 | 판정 |
|---|---|---|---|---|
| **EthIf** | 350 B (기본) | — | **404 B** | **54 B 초과 → 오버플로** |
| EthIf | 1024 B (수정) | 620 B | 404 B | 여유 61 % |
| **tcpip_thread** | 1024 B (기본) | **196 B** | 828 B | 여유 19 %, 위험 |
| tcpip_thread | 2048 B (수정) | 1204 B | 844 B | 여유 59 % |
| defaultTask | 4096 B | 3488 B | 608 B | 여유 85 % |
| ctrl | 2048 B | 1792 B | 256 B | 여유 88 % |
| net | 4096 B | 3092 B | 1004 B | 여유 75 % |
| diag | 2048 B | 1872 B | 176 B | 여유 91 % |

`tcpip_thread` 는 터지지 않았지만 여유가 196 B 뿐이었다. **다음에 터질 자리를
미리 찾은 셈이라 같이 올렸다.** FreeRTOS 힙 48,000 B 중 여유 29,760 B 로
두 스택을 키울 여지는 충분했다.

### 검증 결과

| 항목 | 결과 |
|---|---|
| ping (젯슨 → Front) | **200/200, 0 % 손실**, 평균 0.510 ms / 최대 1.110 ms |
| ping (젯슨 → Rear) | **100/100, 0 % 손실**, 평균 0.365 ms |
| SV 텔레메트리 (5102) | 수신 확인 |
| perf (5104) | Front·Rear 각 1 Hz |
| DTC (5105) | Front·Rear 각 1 Hz |
| CAN 250k 수신 | 79 Hz (IMU 50 + 초음파 17 + 기타) |
| CAN 500k 수신 | 2 Hz — 설계값(500 ms 핑/에코)과 일치 |
| assert / 오버플로 / malloc 실패 | **전부 0** (2,726,662 틱 연속) |
| FreeRTOS 힙 최소 여유 | 29,760 / 48,000 B (62 %) |

### 남긴 계측

진단 장치는 제거하지 않고 남겼다. 이번에 값을 한 것들이다.

- `configASSERT` / `LWIP_PLATFORM_ASSERT` → 파일·줄·태스크명·힙 여유 기록
- `vApplicationStackOverflowHook` → 태스크명 기록 후 정지
- `vApplicationMallocFailedHook` → 횟수 기록 후 정지
- `diag` 태스크가 50 ms 마다 6 개 스레드의 스택 최고수위와 힙 여유 갱신

### 배운 것

**assert 가 가리킨 위치는 오염이 *발각된* 곳이지 *발생한* 곳이 아니다.**
`mem.c` 이중 해제와 `queue.c` 타입 불일치를 각각 개별 버그로 보고 쫓았다면
영원히 못 찾았다. 두 번째 assert 가 "코드상 불가능한 내용" 이었을 때
메모리 오염을 의심하고 **추적을 멈추고 감시 장치부터 켠 것**이 갈림길이었다.

그리고 **켜져 있는 검사와 동작하는 검사는 다르다.**
`configCHECK_FOR_STACK_OVERFLOW = 2` 는 처음부터 켜져 있었다. 훅이 비어
있었을 뿐이다. 감지는 되고 있었는데 아무도 듣지 않았다.

> **자소서 문장 예시**
> "Front 존 컨트롤러를 FreeRTOS + lwIP `NO_SYS=0` 로 전환한 뒤 부팅 1.7 초
> 만에 스케줄러가 정지했다. HardFault 가 아니어서 `configASSERT` 가 파일·줄을
> 기록하도록 고쳤고, lwIP 힙 이중 해제 → FreeRTOS 큐 타입 불일치로 증상이
> 옮겨 다녔다. 두 번째가 코드상 성립할 수 없는 내용이라 메모리 오염으로
> 판단하고, 비어 있던 스택 오버플로 훅을 구현하자 `EthIf` 스레드가 지목됐다.
> 근본 원인은 CMSIS-RTOS v2 의 `stack_size` 가 워드가 아닌 바이트라는 점이었고,
> CubeMX 기본값 350 B 에 대해 실측 사용량은 404 B 였다. 함께 잰 `tcpip_thread`
> 도 여유가 196 B(19 %) 뿐이어서 선제 조정했다. 조치 후 ping 200/200 무손실,
> 270 만 틱 연속 무결함을 확인했다. 부수적으로 발견한 lwIP 코어 락 누락은
> 아직 증상이 없던 Rear 에도 선제 적용했다."

## 6-f. 전환 후 실측 — 그리고 내가 만든 회귀를 찾았다 ★★

RTOS 전환은 §6-c(Rear) / §6-e(Front) 에서 "죽지 않는다"까지 확인했다.
그런데 **성능이 유지되는지는 재지 않았다.** 전환 자체가 목적이 아니었으니
전후 비교를 해야 했다. 재보니 회귀가 있었다.

### 태스크 주기 — 설계값에 수렴

`perf_t_*` 를 ST-Link 로 읽었다. 각 태스크의 **주기**(직전 진입 → 이번 진입)다.

| 보드 | 태스크 | 설계 | min | max | avg | 표본 |
|---|---|---|---|---|---|---|
| Rear | `wheel` | 10 ms | 9,456 | 10,071 | **9,999** | 37,133 |
| Rear | `ctrl` | 10 ms | 9,409 | 10,081 | **9,999** | 37,187 |
| Rear | `net` | 20 ms | 19,277 | 20,404 | **19,996** | 18,621 |
| Rear | `diag` | 50 ms | 49,189 | 50,432 | **49,997** | 7,459 |
| Front | `ctrl` | 10 ms | 9,300 | 10,180 | **9,999** | 37,372 |
| Front | `net` | 20 ms | 19,358 | 21,017 | **19,997** | 18,711 |
| Front | `diag` | 50 ms | 50,632 | 52,543 | 51,045 | 7,344 |

평균이 설계값과 µs 단위로 일치하고 지터는 ±2 % 안이다. 스케줄러는 정상이다.
**여기까지만 봤으면 "전환 성공" 으로 끝냈을 것이다.**

### 지연을 재보니 회귀가 있었다

`cmd_toggle.py` 로 250 회 토글해 지령 → CAN 송신 지연을 쟀다.

```
슈퍼루프 (§5-c)   최대   175 µs   평균     34 µs
전환 후 (최초)   최대 60,036 µs  평균 16,446 µs      <- 480 배 악화
```

두 가지가 겹쳐 있었다. **둘 다 내가 전환하면서 만든 것이다.**

#### 원인 ① — 이벤트 알림을 연결하지 않았다

태스크를 쪼개면서 `Front_CommandEvent()` 를 만들어 `Task_FrontCtrl` 을
깨우도록 해뒀는데, **정작 UDP 수신 콜백에서 부르지 않았다.** 정의만 있고
호출이 없었다. Rear 는 `Rear_BrakeEventFromISR()` 을 콜백 두 곳에서
제대로 부르고 있었는데 Front 만 빠졌다.

```c
/* front_zone_network.c — 빠져 있던 한 줄 */
front_jetson_command_rx_count++;
Front_CommandEvent();   /* CTRL 태스크를 즉시 깨운다 */
```

컴파일러는 아무 말도 하지 않는다. 정의된 함수를 안 부르는 건 문법 오류가
아니고, `static` 도 아니라 "unused" 경고조차 없다.

#### 원인 ② — 스케줄러가 호출당 신호 하나만 보냈다

```c
/* main.c — 슈퍼루프 시절의 설계 */
if ((status == HAL_OK) || (status == HAL_BUSY)) return;   /* 하나 보내고 반환 */
```

하행 명령은 7 종이고 라운드로빈으로 하나씩 내보낸다. 슈퍼루프는 13,900 Hz
로 돌았으니 7 개를 다 보내는 데 ~0.5 ms 였다. **10 ms 주기 태스크로 옮기면
같은 코드가 '대기 신호 수 × 10 ms' 가 된다.**

값이 바뀌어 대기 중인 신호가 남아 있으면 이번 호출에서 마저 내보내도록
고쳤다. 변화 없는 주기 하트비트는 종전대로 하나씩만 보내 버스 부하를
흩뜨린다. 신호별 최소 간격(`MIN_GAP` 10 ms)은 그대로 지킨다.

### 단계별 효과

| 단계 | 평균 | 최대 | 1 ms 초과 |
|---|---|---|---|
| 발견 당시 | 16,446 µs | 60,036 µs | 257 / 455 |
| ① 알림 연결 | 7,300 µs | 50,021 µs | 301 / 653 |
| ② 일괄 송신 | **1,155 µs** | **10,035 µs** | **58 / 655** |

**−93 %.** 남은 최대 10.0 ms 는 `MIN_GAP` 10 ms 와 태스크 주기 10 ms 가
겹친 설계상의 바닥이다.

### 전환 후 지연 전체

| 구간 | min | max | avg | 표본 |
|---|---|---|---|---|
| Front 지령 → CAN 송신 | 16 µs | 10,035 µs | 1,155 µs | 655 |
| Rear 하행 CAN | 10 µs | 99,795 µs | 2,114 µs | 501 |
| **Rear 브레이크 → CAN** | 139 µs | **362 µs** | **208 µs** | 502 |
| Front 종단 폐루프 | 19.4 ms | 40.4 ms | 20.2 ms | 73 |
| Front FDCAN RX ISR | 7 µs | 13 µs | 8 µs | 210,243 |

브레이크만 최대 **362 µs** 로 확연히 다르다. 알림(notify) 디스패치를 쓰는
유일한 경로이고, §6-d 의 A/B/C 실험 결론과 그대로 맞는다. **설계 판단이
실제 운용 수치로 재확인된 셈이다.**

### 스택 실사용 (Front)

| 스레드 | 할당 | 실사용 최대 | 여유 |
|---|---|---|---|
| EthIf | 1,024 B | 404 B | 60 % |
| **tcpip_thread** | 2,048 B | **1,020 B** | 50 % |
| defaultTask | 4,096 B | 608 B | 85 % |
| ctrl | 2,048 B | 280 B | 86 % |
| net | 4,096 B | 996 B | 75 % |
| diag | 2,048 B | 184 B | 91 % |

`tcpip_thread` 가 1,020 B 까지 올라갔다. CubeMX 기본값 1,024 B 로 뒀다면
**여유가 4 B** 였다. §6-e 에서 선제적으로 2,048 B 로 올린 판단이 맞았음이
운용 부하에서 확인됐다.

FreeRTOS 힙 48,000 B 중 최소 여유 29,760 B (62 %), assert·오버플로·malloc
실패 전부 0.

### 배운 것

| 교훈 | 근거 |
|---|---|
| **"안 죽는다" 와 "성능이 유지된다" 는 다른 검증이다** | 전환 후 부팅·ping 만 보고 끝냈으면 480 배 회귀를 몰랐다 |
| **주기가 맞는다고 지연이 맞는 건 아니다** | 태스크 주기는 설계값에 µs 단위로 수렴했는데 지연은 망가져 있었다 |
| **주파수 의존 코드는 태스크로 옮길 때 다시 본다** | "호출당 하나" 는 13,900 Hz 에서만 성립하는 설계였다 |
| **정의만 하고 안 부른 함수는 아무도 안 잡아준다** | 컴파일러 경고 없음. 대조군(Rear)이 있어서 알아챘다 |
| 대조군을 옆에 두면 빠진 것이 보인다 | Rear 는 콜백에서 부르는데 Front 만 없었다 |

> **자소서 문장 예시**
> "RTOS 전환 후 부팅·통신 무결성만 확인하고 넘어갈 뻔했다. 태스크 주기를
> 재보니 설계값에 µs 단위로 수렴해 정상으로 보였지만, 지령 전달 지연을
> 250 회 토글로 측정하자 평균 34 µs 에서 16.4 ms 로 480 배 악화돼 있었다.
> 원인은 두 가지였고 둘 다 내가 전환하며 만든 것이었다 — 태스크를 깨우는
> 알림 함수를 정의만 하고 호출하지 않은 것, 그리고 '호출당 신호 하나'
> 라는 슈퍼루프(13,900 Hz) 전제의 스케줄러를 10 ms 주기 태스크로 그대로
> 옮긴 것이다. 두 가지를 고쳐 평균 1.16 ms 로 93 % 줄였고, 남은 최대
> 10 ms 가 버스 보호용 최소 간격에서 오는 설계상의 바닥임을 확인했다."

## 7. CAN 버스 부하 — 설계 검증

FRONT-CAN 250 kbps, 신호별 주기를 반영한 계산값.

```
프레임 수     427 frame/s
버스 부하     12.06 %  (비트스터핑 최악)
              10.16 %  (평균)
```

일반적 설계 상한 30~40 % 대비 충분한 여유. **"신호 1개 = CAN ID 1개"** 구조로
재설계하면서 프레임 수 증가가 우려됐으나, 계산으로 문제없음을 확인.

**신호 특성별 주기 차등**

| 분류 | 주기 | 대상 |

| ADC | 20 ms | 조향·브레이크·가속·액추에이터 위치 |
| 디지털 상태 | 50 ms | 방향지시등·전조등·override 상태 |
| 진단 | 100 ms | CAN Bus-Off |
| 환경 | 1000 ms | 온도·습도·DHT11 유효 |

## 8. 부수 발견 — 수정했으나 성능 지표 아님

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| D2 SRAM 클럭 | `RCC_AHB2ENR = 0x00000000` (OFF) | `0x60000000` (ON) |
| CAN `AutoBusOff` | RearBody_F407 만 `DISABLE` | 전 노드 `ENABLE` |
| RMII GPIO 속도 | `HIGH` | `VERY_HIGH` |
| PHY 안정화 지연 | 없음 | 500 ms |

**D2 SRAM 클럭**은 이더넷 DMA 디스크립터·RX 버퍼·lwIP 힙이 전부 클럭이 꺼진
메모리에 배치돼 있던 결함. `SystemInit()` 의 활성화 코드가
`#if defined(DATA_IN_D2_SRAM)` 에 막혀 실행되지 않았다.

**AutoBusOff**는 이더넷과 동일한 "리셋해야 산다" 구조의 CAN 판 결함.

## 11. 젯슨 통합 HMI — 진단과 제어를 한 화면에 ★★

`zone_ui.py`(고장 표시)에 액추에이터 제어를 합쳐 `zone_hmi.py` 로 만들었다.
표준 라이브러리(tkinter)만 쓴다. 젯슨에 아무것도 설치하지 않았다.

### 화면 구성

| 영역 | 내용 |
|---|---|
| 좌 | 차량 존 구조도 — 노드/링크를 DTC 상태로 색칠 |
| 우상 | DTC 목록 (코드·상태·발생횟수·검출시간·프리즈 프레임) |
| 하-좌 | FRONT 제어 — 전조등, 방향지시등, 액추에이터(ENABLE + 목표 0~4095), 조향 |
| 하-중 | REAR 제어 — 방향지시등, 브레이크등, 윈도우 |
| 하-우 | 반영 상태 — 보드가 실제로 내리고 있는 값 + 명령 ACK 왕복시간 |

### 설계에서 정한 것

**1. 지령은 주기 재송신한다.** 펌웨어의 `JETSON_COMMAND_TIMEOUT_MS` 가
500 ms 다. 한 번만 보내면 0.5 초 뒤 보드가 링크를 죽은 것으로 보고
오버라이드를 스스로 푼다. UI 는 200 ms 마다(5 Hz) 현재 지령을 되풀이한다.

**2. 놓으면 원상복구가 기본이다.** 체크를 풀면 해당 override 비트가 0 이
되어 보드는 원래 제어원(Front 페달·스위치)으로 돌아간다. 창을 닫을 때도
해제 패킷을 5 회 보내고 종료한다. UI 가 죽어도 500 ms 뒤 자동 복귀한다.
**제어권을 쥐는 쪽이 계속 살아있음을 증명해야 하는 구조**다.

**3. 보낸 값이 아니라 되읽은 값을 보여준다.** 오른쪽 패널의 숫자는 UI 가
보낸 지령이 아니라, H723 이 CAN 으로 F407 에게서 받아온 **실제 출력**이다.
둘이 다르면 하행 경로 어딘가가 끊긴 것이고, 그게 화면에서 바로 보인다.

### 폐루프 검증 — `hmi_selftest.py`

UI 를 클릭하는 대신 `zone_hmi` 의 패킷 생성 함수를 그대로 불러 지령을
내리고, 텔레메트리 되읽기로 말단까지 반영됐는지 확인한다.

```
젯슨 UDP -> H723 파싱 -> CAN 250k -> F407 적용
                                      -> CAN 되보고 -> H723 -> UDP 텔레메트리 -> 젯슨
```

| 시험 | 항목 | 결과 |
|---|---|---|
| 1 | Front 전조등 ON | 되읽기 1 ✓ |
| 1 | Rear 브레이크등 ON | 되읽기 1 ✓ |
| 1 | Rear 방향지시 좌 (모드/좌램프) | 1 / 1 ✓ |
| 1 | Rear 지령출처 = 젯슨 | 1 ✓ |
| 2 | Front 전조등 OFF | 되읽기 0 ✓ |
| 2 | Rear 브레이크등 OFF | 되읽기 0 ✓ |
| 2 | Rear 방향지시 우 (모드/우램프) | 2 / 1 ✓ |
| 3 | 전체 해제 → 지령출처 = Front 복귀 | 제동·방향 모두 0 ✓ |

명령 수신 5 Hz 기준 **불량 카운터 0** (Front `front_jetson_command_bad_count`,
Rear `rear_jetson_command_bad_count`) — 12 바이트 패킷 형식이 양쪽 모두 정확.

### 검증 중에 겪은 것 — 시험 코드가 계속 틀렸다

세 번 연속으로 "제어가 안 된다" 는 결과가 나왔는데, 셋 다 **시험 장치의
결함**이었다. 시스템은 처음부터 정상이었다.

| # | 증상 | 실제 원인 |
|---|---|---|
| 1 | Rear SR 수신 0 개 | `read_until` 두 호출이 **같은 마감시각**을 공유 — 앞의 읽기가 시간을 다 써서 뒤 루프가 한 번도 안 돎 |
| 2 | 모든 되읽기가 0 | 배포한 `hold.py` 가 **0 바이트** — 백그라운드 `&` 가 리다이렉션과 경쟁해 파일을 잘랐다. 지령이 아예 안 나가고 있었다 |
| 3 | 여전히 모든 되읽기가 0 | 송신을 멈추고 읽는 동안 **500 ms 타임아웃으로 보드가 오버라이드를 해제**. 게다가 `read_until` 은 *마지막* 패킷을 돌려주니 항상 해제 후 값을 봤다 |

그 사이 ST-Link 로 H723 내부를 직접 읽어 정상임을 확인했는데, **그 읽기도
처음엔 틀렸다.** `uint8_t` 변수들이 워드 경계에 있지 않은데
`STM32_Programmer_CLI -r32` 는 주소를 워드로 내림한다. 하위 바이트를 그냥
잘라 쓰면 이웃 변수를 읽는다.

```
front_headlamp_override_enable  @0x24000686   (워드 0x24000684 의 3번째 바이트)
front_headlamp_command          @0x24000687   (4번째 바이트)
-> (word >> (8 * (addr % 4))) & 0xFF 로 잘라내야 한다
```

정렬을 보정하고 지령을 **끊김 없이** 유지한 상태에서 읽으니 전 구간이
한 번에 맞았다.

```
override 영역 0x24000684 : 0x01010000  -> headlamp_override=1, headlamp_command=1
override 영역 0x24000688 : 0x01010000  -> turn_override=1,     turn_mode=1(좌)
F407 되보고 0x24000634  : 0x011B0100  -> headlamp_output=1, 온도 28.3 C
F407 되보고 0x24000630  : 0x00010019  -> turn_left_output=1
```

### 배운 것

| 교훈 | 근거 |
|---|---|
| **타임아웃이 있는 제어는 관측 중에도 지령을 유지해야 한다** | 읽는 1 초 동안 보드가 스스로 해제해 0 이 보였다 |
| 상태를 볼 때는 *처음* 오는 새 패킷을 본다 | 마지막을 보면 조건이 끝난 뒤의 값이다 |
| 적체된 패킷을 먼저 버린다 | 지령 이전 값을 읽고 "반영 안 됨" 으로 오판 |
| **배포가 됐는지부터 확인한다** | `wc -c` 한 번이면 0 바이트를 바로 잡았다 |
| 정렬을 모르면 바이트를 읽을 수 없다 | `-r32` 는 워드로 내림한다 |
| 시험이 실패하면 시험을 먼저 의심한다 | 4 건 전부 시험 장치 결함이었다 |

> **자소서 문장 예시**
> "젯슨에 진단·제어 통합 HMI 를 만들었다. 표시만 하는 것이 아니라 전조등·
> 방향지시등·브레이크등·윈도우·액추에이터를 UDP 로 내리고, 그 결과를 CAN
> 되보고 기반 텔레메트리로 되읽어 '보낸 값' 이 아닌 '실제 출력' 을 보여준다.
> 펌웨어의 500 ms 링크 타임아웃에 맞춰 5 Hz 로 지령을 재송신하고, 체크를
> 풀거나 UI 가 죽으면 보드가 자동으로 원래 제어원에 복귀하도록 설계했다.
> 검증은 UI 를 클릭하는 대신 같은 패킷 생성 함수를 불러 자동화했고, 8 개
> 항목 전부 폐루프로 통과했다. 이 과정에서 나온 '제어 안 됨' 결과 4 건은
> 모두 시험 장치의 결함이었으며, 특히 관측을 위해 송신을 멈춘 순간 보드가
> 타임아웃으로 오버라이드를 해제해 항상 0 이 읽히던 문제가 대표적이다."
